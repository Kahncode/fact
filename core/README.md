# fact-core

Shared foundation: settings, logging, database, migrations, project config, shared types and the activity contract, GitHub App access.

## Settings

`fact.core.settings.get_settings()` loads the factory settings from `fact.yaml` (layering in `AGENTS.md`); routing, step limits and the per-project cap are project config, not settings. Scheduler settings: `concurrency.scheduler_interval_seconds` (default 30: how often the API's tick loop runs, dev only), `concurrency.max_failed_runs` (default 3: failed runs in a row before the scheduler stops retrying a task). Usage gate settings: `claude.usage_gate` (default true) and `claude.reserve.five_hour` (0.10) and `claude.reserve.weekly` (0.05, for `seven_day`, `seven_day_opus` and `seven_day_sonnet`), the share of each window fact leaves to the person. `worker.keep_awake` (default true) keeps Windows awake while runs are active. `Settings.api_url` is the base URL clients use to reach the API (`http://<host>:<port>` from `api`; a wildcard bind host `0.0.0.0` or `::` becomes `127.0.0.1` or `::1`, IPv6 literals are bracketed). The worker and the `fact` CLI use it; don't rebuild the URL from `api.host`. `project_path(ref)` gives a project's local checkout from its `path` (relative to the folder of `fact.yaml`), or None.

## Database

Plain SQLAlchemy 2 async ORM on SQLite (aiosqlite). `fact.core.db` has `Base` (constraint naming convention), `database_url(settings)`, `create_engine(url)` (sets `foreign_keys=ON` and `journal_mode=WAL` on connect) and `session_factory(engine)`.

### Models

`fact.core.models` has `Project`, `Repository`, `Run`, `Step`, `Event`, `Notification` (a run's `gate_waiting`, `prs_ready`, `run_failed`, `run_finished` or `task_held` message for a person; `run_id` nullable, `read_at` set once read, `dedupe_key` unique so one notification exists per run state) and `UsageWindow` (table `usage_windows`: the last state an agent step reported of one subscription window, unique by `account` and `window`; `utilization` 0..1, `resets_at`, `updated_at`) and `SchedulerSwitch` (table `scheduler_switch`, dev only: one row, `id` 1, whose `on` is `fact scheduler on|off`; no row means on; read by `fact.api.scheduler_switch`); `Run.trigger` (M2-14) is a `RunTrigger`, `manual` (`fact run`) or `scheduler`; rows from before it are `manual`. Steps and runs carry `tokens_in`, `tokens_out` and `cache_read_tokens`/`cache_write_tokens` (parts of `tokens_in`); `Step.cost_usd` is NULL when the harness reported no cost (never 0), `Step.usage_partial` marks a session cut short, `Step.turns` and `Step.peak_context_tokens` (nullable, NULL for steps without an agent session) are an agent session's model calls and the input of its largest turn, and `Run.cost_unknown_steps` counts agent steps without a cost. `fact.core.enums` has the `StrEnum`s (`RunStatus`, `RunOutcome`, `RunTrigger`, `StepKind`, `StepStatus`, `StepOutcome`, `NotificationKind`), stored as plain strings with no DB check. Only Postgres-compatible types are used (`String`, `Text`, `Integer`, `Float`, `Numeric(12, 6)` for USD, `DateTime(timezone=True)`, `JSON`). SQLite returns naive datetimes; treat them as UTC. New models must be imported in `migrations/env.py` (via `fact.core.models`) so autogenerate sees them.

### Migrations

Alembic lives in `core/migrations/`, configured by `core/alembic.ini`. The URL comes from settings (`<data_dir>/fact.db`) and the data dir is created if missing. Run from the repository root:

```
uv run alembic -c core/alembic.ini current
uv run alembic -c core/alembic.ini revision --autogenerate -m "message"
uv run alembic -c core/alembic.ini upgrade head
```

In code: `fact.core.migrate.upgrade(url)`. It is synchronous (the async `env.py` starts its own event loop), so don't call it from a running loop. Set `FACT_DATA_DIR` to point commands at another data dir.

## Project config

`fact.core.project_config` loads `<home>/.fact/project.yaml` (`load_project_config(home_path)` -> `ProjectConfig`) and `<repo>/.fact/repo.yaml` (`load_repo_config(repo_path)` -> `RepoConfig`; commands are argv lists, never strings). Invalid or missing files raise `ConfigError` with the file path and field. Besides repositories, task source, workflows and merge policy, `ProjectConfig` holds `runner_pool` (`RunnerPoolConfig`: `kind` `local` and `max_concurrent_runs`, the only scheduler cap, runs queued, running or waiting; default 2), `routing` (`RoutingConfig` from `fact.core.types`) and `step_defaults` (`StepDefaultsConfig` from `fact.core.step_defaults`: per-kind overrides, every value None unless set; the defaults are `fact.sdk.step_defaults.SDK_STEP_DEFAULTS`). This repository's own `.fact/` is the first project.

## Task sources

Callers reach a project's tasks through `fact.core.tasks.source_for(project_config, settings, root=None, *, app=None)`, which returns a `TaskSource` (async `list_ready()` returning `ReadyItem`s with their dependency depth; `list_ready(include_waiting=True)` also returns the tasks whose dependencies are not done, with `waiting_on`, for the scheduler's preview; `get(key)`, `deps_done(task)`, write-back `comment`, `set_labels`, `write_context`, `link_prs`, `close`, and sync `mark_done(worktree, key)`): a `FileTaskSource` on `root` for `files`, a `GitHubIssuesSource` for `github` (with `app`, else `fact.core.github.shared_app(settings)`, which raises `GitHubAppConfigError` while the App is not configured). `parse_key(key)` parses `task:M1-02` and `gh:owner/repo#12` into a `TaskKey`; `branch_name(key)` gives `fact/task-m1-02` or `fact/gh-12`; `dependency_key(task, dep)` turns a bare dependency id into a key of the task's own source. `fact.core.tasks.events.report(source, ReportStatusInput)` maps a run event to write-backs: `run_started` adds `fact:running` and comments the run link; `gate_opened` adds `fact:needs-human` and comments what the gate needs; `gate_answered` removes `fact:needs-human`; `prs_opened` links the PRs; `merged` closes the task and removes both labels; the run ends the scheduler does not retry (`stopped`, `needs_human`, `pr_opened`, `closed`) hold the task with `hold(source, key, comment)`: add `fact:needs-human` (keeping `fact:ready`), remove `fact:running` and comment the end, why it is held and how to release it (remove the label or `fact run`). `fact.core.holds` has that wording (`HELD_ENDS`, `held_text`, `release_hint`), free of I/O so workflow code imports it. A `GitHubIssuesSource` task has `Task.needs_human` set when the issue carries `fact:needs-human`; `is_issue(key)` tells an issue key from a file task's. Only `fact.core.tasks` and tests import `FileTaskSource`.

`fact.core.tasks.FileTaskSource(root)` reads `tasks/` (format in `tasks/README.md`) and implements `TaskSource`; its write-backs only log (`task_write_back_skipped`). Sync readers: `all()`, `find(key)`, `status(key)`, `all_deps_done(task)`, `ready()`, `validate()` (list of error strings) and `mark_done(worktree, key)` (deletes the task's file under `worktree` and returns its path) and `depths()` (each task's dependency depth by key: 0 with no dependency still in the folder, else one past its deepest dependency; a cycle is cut where it closes). Statuses are not on `Task`; use `status()`. A dependency whose file is missing counts as done if its number is below the highest remaining one in its milestone, or its milestone is below the highest present.

`fact.core.tasks.GitHubIssuesSource(repo, app)` (`github_issues.py`, M2-09; write-backs in `github_writes.py`, M2-11) reads one repository's issues (`gh:owner/repo#12`, branch `fact/gh-12`). `list_ready()` gives the open `fact:ready` issues (PRs excluded) whose dependencies are done, at depth 0. `get(key)` reads an issue of its own repository, open or closed (None for a PR, an unknown issue, another repository's or a file key): type from `type:*` (`type:incident` is `bug`, unknown is `feature`), complexity from `complexity:*` (default `standard`), acceptance criteria from the checklist under an "Acceptance criteria" heading of any level, `depends_on` from the blocked-by links (`issues/{n}/dependencies/blocked_by`, paginated) then `Depends on #3, owner/other#4` lines, deduplicated, as full `gh:` keys. A dependency is done when closed as completed or closed with no `state_reason`, or a merged PR; `not_planned` and `duplicate` are not done, and an unreadable one (404, App not installed) is not done and logs `task_issue_unreadable`. Issue payloads are cached per instance, so use one instance per request or tick. `mark_done` returns None.

Its write-backs (`GitHubIssueWrites`, a mixin) go to the repository the key names, with that repository's installation token. `comment` posts an issue comment; `set_labels` posts the labels to add and deletes each label to remove (a 404, label absent, is ignored); `link_prs` posts one comment listing the PRs, nothing when there are none; `close` sets the issue `closed` with `state_reason` `completed`; `write_context` reads the body afresh and patches it only when `with_context(body, section)` changed it. `with_context` puts the section between `<!-- fact:context:start -->` and `<!-- fact:context:end -->`: the last start marker followed by an end marker delimits it; with no such pair (no markers, a lone start, a lone end, an end before the start) a fresh pair is appended and stray markers stay; every byte outside the section is preserved. A key that is not `gh:` (a file task run on a project whose source is GitHub) is only logged (`task_write_back_skipped`), not an error.

## Shared types

`fact.core.types` (re-exported as `fact.sdk.types`) holds the frozen Pydantic models that cross the Temporal boundary: `Task`, `RepoCheckout`, `WorkspaceSpec`, `WorkspaceHandle`, `Usage`, `StepResult`, `PRRef`, `RunInput`, `RunResult`, plus `ArtifactRef` (a str key). They hold artifact refs, never raw logs, transcripts or diffs. Pass any text going into a payload through `limit_text(s, max_bytes)`, which cuts on a character boundary; `StepResult.summary` and `RunResult.summary` are capped at 2048 bytes (a validator rejects longer text; cut it with `limit_text`). `RunInput` carries `home_repo` (the repository holding `.fact/`; default the first) and the project's `routing` and `step_defaults` overrides, filled by whoever starts the run from the project config so workflow code reads no config (the SDK resolves the limits over its defaults), and `handoff_ref` (artifact key of the handoff note a stopped run of the task left, or None). `RunOutcome` includes `pr_opened` (change set open for review), `needs_human` (the run stopped for a person, such as an exhausted checks loop, or a person who stopped the run instead of answering a blocked agent's question) and `stopped` (a person stopped the run with `fact stop`, or rejected its plan). `WorkspaceSpec.sandbox` (name under `.fact/sandboxes/`; None: the pool's `default_sandbox`, filled by the version's `prepare_workspace`) and `sandbox_args` (extra `docker run` arguments) come from the workflow's `FactWorkflow.sandbox`/`sandbox_args`. `WorkspaceHandle.branches` maps each repository's full name to the branch actually checked out: the requested one, or `<branch>-<n>` when another workspace holds it.

## Activity contract

`fact.core.activity_contract` is the contract between workflow code (`fact.sdk`) and the worker: the task queues (`CONTROL_QUEUE`, `SANDBOX_QUEUE`), activity names (`prepare_workspace`, `teardown_workspace`, `agent_step`, `shell_step`, `open_change_set`, `mark_task_done`, `record_run_started`, `record_run_finished`, `record_gate_opened`, `record_gate_answered`, `notify`, `write_handoff`, among others), the `Check` literal and the frozen input models (`AgentStepInput`, with `handoff_ref`, `ShellStepInput`, `CheckResult`, `OpenChangeSetInput`, `MarkTaskDoneInput`, `RunStartedInput`, `RunFinishedInput`, `GateOpenedInput`, `GateAnsweredInput`, `NotifyInput`, `HandoffInput` and `HandoffStep` for a stopped run's handoff note, `ReportStatusInput` for `report_status`). The input models live in `fact.core.activity_inputs` and are re-exported. `ACTIVITY_SPECS` gives every activity name an `ActivitySpec` (zone `control` or `workspace`, default `max_duration`, `Retry`, cancellation `wait` or `try`; `spec_for(name)` raises `UnknownActivityError`), with `HEARTBEAT_INTERVAL` (30 s) and `HEARTBEAT_TIMEOUT` (2 min) for all of them. Workflows call activities by these names, so `fact.sdk` never imports `fact.worker`.

## Gates, status and steering

`fact.core.gates` is the contract between a running workflow and whoever talks to it: the handler names `ANSWER_GATE` (`answer_gate`, an update taking a `GateAnswer`), `STATUS` (`status`, a query returning `WorkflowStatus`) and `STEER` (`steer`, a signal taking the text to add to the next agent session), so the API and CLI can call them by name without importing `fact.sdk`. Models: `GateDecision` (`approve`, `reject`), `GateAnswer` (`gate_id`, `decision`, `note` up to `NOTE_MAX_CHARS` 4000), `OpenGate` (`gate_id`, `kind`, `stage_id`, `attempt`, `details`, `opened_at`), `StageOutcome` and `WorkflowStatus` (`stage`, `attempt`, `gate`, `outcomes`); `STEER_MAX_CHARS` is 8000. They are re-exported from `fact.sdk.types`; the handlers are implemented by `fact.sdk.human.HumanSteps`.

## Scheduler

`fact.core.scheduler` is the scheduler's contract: `SCHEDULE_ID` (`fact-scheduler`, the retired Temporal Schedule the worker deletes at start), and the models `ReadyTask` (`project`, `task_key`, `task_id`, `depth`, `waiting_on`, `failed_runs`, `last_run_id`, `hold`), `ProjectLoad`, `ReadyTasks`, `PlannedTask` (`task`, `hold`, `detail`), `RunRecord` and `TickResult` (`started`, `failed`, `usage_full`, `skipped`). `Hold` says why a ready task does not start: `needs_human` (an issue carrying `fact:needs-human`), `parent`, `dependency`, `failure_cap`, `cap` or `usage`. All functions are pure; the API's tick (`fact.api.scheduler.run_tick`) and preview call them:

- `run_history_hold(newest_first, max_failed, *, labelled=False)` gives `(offered, failed_runs, hold)`: not offered with a run in progress, nor, for a file task (`labelled` False), with a last run that ended other than `failed`; otherwise offered, held `failure_cap` once `max_failed` failed in a row, counted back to the newest run that did not fail and the newest `manual` run. An issue (`labelled`) is held by its `fact:needs-human` label instead, so its history holds nothing else.
- `effective_priorities(tasks)` sets each task's `effective_priority`: the highest of its own `priority` and that of every task of the same project waiting on it, directly or transitively (`waiting_on`).
- `plan(ready, usage_full="")` orders each project's candidates by effective priority, then dependency depth, then id (`M<n>-<n>` numerically, then issue numbers), and lets the projects take turns in name order for the slots, keeps the holds the API set, then holds `cap` past the project's runner pool `max_concurrent_runs` (counting runs queued, running or waiting; a project missing from `projects` gets nothing), and `usage` on the rest when `usage_full` is set. `plan_starts(ready)` is the tasks `plan` leaves unheld; the tick checks the usage gate only when it is not empty.

`fact.core.usage_gate` holds the gate's models: `GateState` (`ok`, `full`, `unavailable`, `off`), `GateWindow` and `UsageCheck` (`held(now)`: full with `next_call_at` ahead), and `reserves`, `thresholds` (`1 - reserve` per window, for `ClaudeUsage.full(thresholds)`), `gate_windows` and `full_reason`. The API runs the tick and keeps the cached gate answer (`fact.api.usage_gate`).

## GitHub

`fact.core.github` authenticates as the fact GitHub App. Configure it with `FACT_GITHUB_APP_ID` (the App ID or the Client ID; both work as the JWT issuer) and `FACT_GITHUB_APP_PRIVATE_KEY_PATH` (a PEM file outside any repository; a relative path resolves from the folder of `config_file()`, the default `fact.yaml` or `FACT_CONFIG`, like `.env`, even when `from_settings` gets a `Settings` object). `github_api_url` defaults to `https://api.github.com`.

- `GitHubApp.from_settings()` builds the App (raises `GitHubAppConfigError` if unset or the key is unreadable). Caches live on the instance: keep one `GitHubApp` per process. `shared_app(settings=None)` returns that one instance, built on first use and cached per App id, key path and API URL (an unconfigured App raises and is tried again on the next call); the worker and `source_for` use it.
- `app_jwt()` signs an RS256 App JWT (issued 60 s in the past, valid 9 minutes). `app_info()` and `installation(owner/repo)` read `/app` and the repository's installation.
- `installation_token(owner/repo)` returns an `InstallationToken(token, expires_at, installation)` that can reach only that repository. It is cached per repository (case-insensitive) until 5 minutes before expiry; concurrent calls for one repository mint once.
- `bot_identity()` gives the commit author: `<slug>[bot]` and `<user id>+<slug>[bot]@users.noreply.github.com` (unauthenticated user lookup; GitHub Enterprise Server is not supported).
- `github_client(token, *, api_url)` is a plain `httpx.AsyncClient` with bearer auth and the GitHub API headers (version `2022-11-28`), following redirects. Error responses raise `GitHubAuthError` (401), `GitHubForbiddenError` (403), `GitHubNotFoundError` (404) or `GitHubError`, with a hint, the method, path and GitHub's message.
- `GitHubApp.api_client(token)` returns a `github_client` on the App's API URL (and its test transport); the worker's `open_change_set` uses it.
- `sync_labels(client, owner/repo)` (`labels.py`) creates every label in `FACT_LABELS` (`fact:*`, `type:*`, `complexity:*`) on a repository and fixes colour, description and case of existing ones (names match case-insensitively). It never deletes a label and returns one `LabelChange` (`created`, `updated`, `unchanged`) per label. `split_full_name(owner/repo)` validates and splits a repository name.

Tokens never appear in logs or `repr()`; minting logs `github installation token minted` with the repository, installation id and expiry. Check a setup with `uv run fact github check <owner/repo>`; create fact's labels on a repository with `uv run fact github labels sync <owner/repo>`.

## Artifacts

`fact.core.artifacts` is the artifact store: the `ArtifactStore` protocol (`put_bytes`, `put_file`, `open`, `exists`), `LocalArtifactStore(root)` (rooted at `settings.artifacts_dir`) and `step_key(run_id, stage_id, attempt, name)` giving `runs/<run>/<stage>/<attempt>/<name>`, and `handoff_key(run_id)` giving `runs/<run>/handoff.md`, the note a stopped run leaves for the next run of its task (derived from the run id, so it needs no DB column). Keys with `..`, empty segments, absolute paths or drive letters raise `InvalidArtifactKeyError` (the API answers 400). The API serves them at `PUT`/`GET /api/v1/artifacts/{key}`.

## HTTP retry

`fact.core.http_retry` keeps the API's clients working while the API restarts (an upgrade). `AsyncRetryTransport` and `RetryTransport` wrap an httpx transport and retry with backoff (0.25 s doubling to 5 s) until a `RetryPolicy` budget has passed since the first attempt: on `ConnectError`/`ConnectTimeout` for any method, and on 502/503/504 only for a body that can be sent again (and, with `statuses_any_method=False`, only for idempotent methods). `WORKER_POLICY` (60 s, any method) is used by `fact.worker.client.api_http`; `CLI_POLICY` (5 s, idempotent methods only, so `POST /runs/start` is never resent after a 502) by the CLI's `projects.make_client`.
