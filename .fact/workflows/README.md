# Workflows

This project's workflow code (`*.py`), loaded by its workflow worker from a checkout of this repository. Each workflow subclasses `FactWorkflow` from `fact.sdk.workflow`, declares its stages with `@stages([...])` and imports shared types from `fact.sdk.types`.

- `standard.py`: `Standard` (Temporal type `standard`). When the run's `require_plan_approval` is on, an `approve_plan` gate comes first, before any workspace exists (stage and id `approve_plan`, details `summary`, `title`, `path`, `acceptance_criteria`): approve goes on, reject ends the run `stopped`. This project's `project.yaml` turns it off, because setting `status: ready` on a task file is already the approval. Prepare the workspace, run `implement`, loop lint and test with `fix_checks` sessions (at most 3) until green, then one `review` session (stage `review`, opus via `.fact/project.yaml` routing) against the acceptance criteria and the repository's rules. If a criterion is unmet or a finding is medium or high, an `address_review` session fixes them and the check loop runs again (one review round in v0). Then a `learn` session updates `CLAUDE.md`, `docs/` and READMEs on the branch and writes the PR title and summary (falling back to the implement session's, then the task title, when it gives none or does not pass); mark the task done on the branch, open the PR with the review's criteria table. Then `until_ci_green` waits for CI on the PR's head commit (stage `wait_for_ci`); a failure goes to a `fix_ci` session with the failing jobs' links and log tails, whose commit is pushed to the PR (the next `open_pr` attempt) before CI is awaited again, at most `MAX_CI_FIX_ATTEMPTS` (2) times. When the checks loop, the base sync or the CI loop gives up (fixes exhausted, a fix session that does not pass, a CI fix that commits nothing, CI that never finishes, conflicts still there after `MAX_BASE_SYNCS` merges), the run ends `needs_human` with no gate; the run-end hold says why on the issue. An agent session answering `blocked` with a `question` asks it on the task (`fact.sdk.asking`, through `FactWorkflow.agent`): a `needs_human` gate opens (stage `needs_human`, id `<stage>-question-<n>`, details `summary`, `question`, `stage`), the question is posted on the issue with `fact:needs-human`, and the run waits for maintainers' comments mentioning the App (`@sofact-dev`; `wait_for_answer`, polled every 60 s). Each new batch goes to an `answer` session (stage `answer`, `converse`): `continue` removes the label and resumes the blocked session with its instructions and the thread, `ask` posts its reply and waits again, `stop` ends the run `needs_human`. `fact gate approve|reject` answers it too and wins (approve resumes the session with the note); a file task waits on `fact gate` only. Instructions sent with the `steer` signal reach the resumed session. Once CI is green, `FactWorkflow.classify` routes the change set (`fact.sdk.classify`): `classify_signals` raises the rules' signals, a read-only `classify` session (stage `classify`) rates risk, door and security findings, `fact.sdk.classification.decide` picks `human_review` when any signal holds (spec ambiguous, a security finding, schema change, API change or break, always-review path, task closed, high risk, one-way door, or no valid answer from the session or the rules), else `auto_merge`, and `label_change_set` (stage `label_prs`) labels each PR `fact:needs-review` or `fact:auto-merge`, adds a `## Review` section to its description and records the classification in its step outputs. Then a change set routed `auto_merge`, when the run's `auto_merge` (the project's setting) is on, is merged by `Standard` itself through `merge_change_set` (the project's `merge_method`, each PR only at the head commit CI passed on) and the run ends `merged` with no `prs_ready`; otherwise (routed `human_review`, auto-merge off, or GitHub refuses the merge) the PRs are relabelled `fact:needs-review` with why (`route_to_review`), a `prs_ready` notification with the classification's reasons is sent and each PR follows GitHub's review flow (`until_reviewed`; each wait is stage `wait_for_review`, a gate-like step counted as human wait time, which `answer_gate` cannot answer; polled every 60 s, 30 days in all): an approval on the PR's head waits for CI there (a CI fix moves the head and needs a new approval) and merges that PR alone with the project's `merge_method`, whatever `auto_merge` says; a review requesting changes gets one `review_reply` session (stage `review_reply`, `converse`) whose replies fact posts as `fact[bot]` in their threads, and whose `implement` decision runs implement (with the review as `$context`), checks, review, learn, a push to the same PR and CI again, never classifying, while `reply` changes nothing; then review is re-requested from the reviewer. Once every PR is merged or closed the workspace is torn down. `Standard` posts no cost comment itself: `FactWorkflow.execute` posts it once, as the run's last step, on every PR the run opened, whatever the outcome (stopped and failed included). `agent` resumes a session once when the worker stopped during it or the agent reports a temporary, retryable block (see `fact.sdk.sessions`); a session the Claude usage limit refused waits, with the run marked waiting (`usage limit until <time> UTC`), until the limit resets and is resumed, up to 20 times before the step ends `needs_human` (see `fact.sdk.agents`). Outcomes: `merged` (every PR merged, by a person or by fact once approved); `closed` (a PR closed without merging); `needs_human` (an agent reported itself blocked without a question, or a person stopped it instead of answering: no PR before it opened; checks out of attempts: no PR; CI or the base sync out of attempts: PR open, workspace kept); `failed` (an agent session errored or hit its turn limit, including a review without a valid structured answer, or the wait for review failed: 30 days passed or GitHub refused); `stopped` (the plan was rejected: summary `plan rejected: <note>`, no workspace, no PR; or a person stopped the run with `fact stop`: summary `stopped: <reason>` (or `stopped`), a handoff note written to `runs/<run_id>/handoff.md`, the workspace torn down, the remote branch and PR kept for the next run of the task, which gets the note as `$handoff`; a stop that arrives once the PR is merged, closed or abandoned keeps that real outcome). Notifications (best effort, one per run state): each gate (`approve_plan` or `needs_human`) notifies `gate_waiting` when it opens; `prs_ready` (linking the first PR) goes out once CI is green, before the wait for review; at the end `run` calls `notify_run_end`, which sends `run_failed` for `failed` or `needs_human` and `run_finished` for `merged`, `closed` or `stopped`, also when the run fails with an exception, before it is re-raised. Task status (best effort, through `FactWorkflow`, not `Standard` itself): the run's start, each gate opening and its answer, the opened PRs, and every end but `failed` are reported to the task's source (`report_status`); a GitHub issue gets labels, comments and, on `merged`, closed; a `stopped`, `needs_human`, `pr_opened` or `closed` end holds the task with `fact:needs-human` and also sends one `task_held` notification.

Workflow code is replayed by Temporal: no I/O, clock or settings reads; timeouts come from `RunInput.step_defaults` resolved over `fact.sdk.step_defaults.SDK_STEP_DEFAULTS` (`fact.sdk.step_defaults.resolve`). `uv run pytest worker/tests/test_standard_workflow.py` replays a fresh green run to check the workflow stays deterministic.

`python -m fact.worker` loads these files from a detached checkout of the default branch's SHA (`pinned_dir/projects/<project>/<sha>`) and runs them on task queue `wf-<project>`, pinned to that version (see `worker/README.md`). Files starting with `_` are skipped; a file that fails to import stops the whole project from loading. Only classes that subclass `FactWorkflow` and are decorated with `@workflow.defn` themselves are registered. A change merged to the default branch takes effect at the next worker restart; runs already pinned to the old version then wait: no worker of their version runs, so `fact stop` cannot end them, and they are cleaned up by hand (delete `<data_dir>/workspaces/<run_id>`) before a restart. Stop runs with `fact stop` before restarting the worker instead. That includes a run waiting for review: after merging its PR, wait until it shows `merged` (within about 60 s) before restarting the worker.
