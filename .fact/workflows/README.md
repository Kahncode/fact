# Workflows

This project's workflow code (`*.py`), loaded by its workflow worker from a checkout of this repository. Each workflow subclasses `FactWorkflow` from `fact.sdk.workflow`, declares its stages with `@stages([...])` and imports shared types from `fact.sdk.types`.

- `standard.py`: `Standard` (Temporal type `standard`). When the run's `require_plan_approval` is on, an `approve_plan` gate comes first, before any workspace exists (stage and id `approve_plan`, details `summary`, `title`, `path`, `acceptance_criteria`): approve goes on, reject ends the run `dropped`. This project's `project.yaml` turns it off, because setting `status: ready` on a task file is already the approval. Prepare the workspace, run `implement`, loop lint and test with `fix_checks` sessions (at most 3) until green, then one `review` session (stage `review`, opus via `fact.yaml` routing) against the acceptance criteria and the repository's rules. If a criterion is unmet or a finding is medium or high, an `address_review` session fixes them and the check loop runs again (one review round in v0). Then a `learn` session updates `CLAUDE.md`, `docs/` and READMEs on the branch and writes the PR title and summary (falling back to the implement session's, then the task title, when it gives none or does not pass); mark the task done on the branch, open the PR with the review's criteria table and comment the run's cost on it. Then `until_ci_green` waits for CI on the PR's head commit (stage `wait_for_ci`); a failure goes to a `fix_ci` session with the failing jobs' links and log tails, whose commit is pushed to the PR (the next `open_pr` attempt) before CI is awaited again, at most `MAX_CI_FIX_ATTEMPTS` (2) times. When the checks loop or the CI loop gives up (fixes exhausted, a fix session that does not pass, a CI fix that commits nothing, CI that never finishes), a `needs_human` gate opens (stage `needs_human`, id `checks-<n>` or `wait_for_ci-<n>`, details `loop` and `summary`) and the run waits, at no cost, for an `answer_gate` update: approve runs that loop once more, and instructions sent with the `steer` signal reach its fix sessions; reject ends the run. Once CI is green, the cost comment is updated, a `prs_ready` notification sent, and the run waits (stage `wait_for_review`, a gate-like step counted as human wait time, which `answer_gate` cannot answer) until every PR is merged or closed, polled every 60 s for up to 30 days; the cost comment is updated once more and the workspace torn down. A rejected CI gate also updates the cost comment. `agent` resumes a session once when the worker stopped during it or the agent reports a temporary, retryable block (see `fact.sdk.sessions`). Outcomes: `merged` (every PR merged); `closed` (a PR closed without merging); `needs_human` (implement, review or address-review reported itself blocked: no PR; a rejected checks gate: no PR; a rejected CI gate: PR open, workspace kept; the summary ends `; rejected: <note>` when the answer has a note); `failed` (an agent session errored or hit its turn limit, including a review without a valid structured answer, or the wait for review failed: 30 days passed or GitHub refused); `dropped` (the plan was rejected: summary `plan rejected: <note>`, no workspace, no PR; or a person dropped the run with `fact drop`: summary `dropped: <reason>` (or `dropped`), a handoff note written to `runs/<run_id>/handoff.md`, the workspace torn down, the remote branch and PR kept for the next run of the task, which gets the note as `$handoff`; a drop that arrives once the PR is merged, closed or abandoned keeps that real outcome). Notifications (best effort, one per run state): each gate (`approve_plan` or `needs_human`) notifies `gate_waiting` when it opens; `prs_ready` (linking the first PR) goes out once CI is green, before the wait for review; at the end `run` calls `notify_run_end`, which sends `run_failed` for `failed` or `needs_human` and `run_finished` for `merged`, `closed` or `dropped`, also when the run fails with an exception, before it is re-raised.

Workflow code is replayed by Temporal: no I/O, clock or settings reads; timeouts come from `RunInput.limits`. `uv run pytest worker/tests/test_standard_workflow.py` replays a fresh green run to check the workflow stays deterministic.

`python -m fact.worker` loads these files from a detached checkout of the default branch's SHA (`pinned_dir/projects/<project>/<sha>`) and runs them on task queue `wf-<project>`, pinned to that version (see `worker/README.md`). Files starting with `_` are skipped; a file that fails to import stops the whole project from loading. Only classes that subclass `FactWorkflow` and are decorated with `@workflow.defn` themselves are registered. A change merged to the default branch takes effect at the next worker restart; runs already pinned to the old version then wait: no worker of their version runs, so `fact drop` cannot end them, and they are cleaned up by hand (delete `<data_dir>/workspaces/<run_id>`) before a restart. Drop runs with `fact drop` before restarting the worker instead. That includes a run waiting for review: after merging its PR, wait until it shows `merged` (within about 60 s) before restarting the worker.
