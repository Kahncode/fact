**Also decided**

- **Hosting**: local-first for the first versions only. Remote hosting (Linux) and more users come later, so nothing in v0 may assume one machine forever.
- **Platforms**: v0 runs on your Windows PC but must run on Windows, macOS and Linux. Tooling is cross-platform Python (no bash or make), paths use `pathlib`, and containers rely on Docker Desktop on Windows and macOS. CI (26 Nov 2026): PRs are checked on Linux only and every check must pass to merge; Windows runs on `main` after each merge (and by hand), so a Windows break shows as a red `main` before a new factory version is pinned.
- **Repository**: one monorepo, [Kahncode/fact](https://github.com/Kahncode/fact): a uv workspace of Python packages `core/`, `api/`, `worker/`, `sdk/` and `cli/` (namespace `fact.*`, each with its own `tests/`), plus `web/` for the UI, `docs/spec/` for this spec and `tasks/` for the bootstrap tasks.
- **Auto-merge**: ~~none in v0~~ Reopened 26 Nov 2026: from M3, a project setting on by default; classify decides per change set, and fact's own repository is classified like any other (`06-workflow-authoring.md`, `14-dogfooding-and-safety.md`).
- **Concurrency (27 Nov 2026)**: one cap, `max_concurrent_runs`, per runner pool, configured with the project's pool; no factory-wide or separate project cap. Each run holds one runner (its workspace) from start to end. Default: 2 concurrent runs on your PC. A planner is a runner running another workflow, with no cap of its own.
- **Claude Code**: runs headless under your logged-in subscription in v0. From M2, fact reads Claude Code's actual usage and windows, starts new runs only when the window allows, and a step that hits the limit waits for the reset and resumes.
- **Context**: lives in the repositories; every workflow has a learn step after review.
- **Scoring and benchmarks**: needed soon after v0 to measure whether changes to fact itself (prompts, workflows, models) make it better.
- **Spec in the repository:** this spec is copied to docs/spec/ in M0; from then on the repository copy is the source of truth and agents keep it current.
- **Bootstrap tasks:** until fact ingests GitHub Issues, tasks are markdown files in tasks/\<milestone>/, one file per commit with its context update, dependencies in front matter. Claude Code runs them until fact can.
- **Planner:** its own milestone (M6). Until then Claude Code in the repository is the planner, with skills.
- **Missing task files:** a dependency id whose task file is gone counts as done if its number is below the highest remaining one in its milestone, or its milestone is below the highest present (`FileTaskSource`, M1-02). Finished tasks can then be deleted without rewriting `depends_on`. Cost: `validate()` cannot catch typos below that bound; ids above it are errors. `validate()` runs as a CI test on the real `tasks/` folder.
- **Parent issues (26 Nov 2026):** fact runs only `fact:ready` issues; a sub-issue also needs every ancestor `fact:ready`, so a parent's label gates its plan. A parent's open sub-issues are its dependencies; it then runs as a normal task, and a run with nothing to do ends `no_changes` (success, warning notification). A parent without a work type is closed without a run. An ancestor's own dependencies (blocked-by links, `Depends on` lines) hold its sub-issues too (27 Nov 2026). Details in `08-planning.md`.
- **Epic is a label for people (27 Nov 2026):** fact never reads `type:epic`. A parent's work type (its other `type:*` label) decides: with one it runs once its sub-issues are closed, without one it is closed without a run. A parent of epics is an epic, and a parent with work of its own carries `type:epic` beside its work type. Why: with one `type:*` per issue a parent had to choose between being shown as an epic and having its final pass run, and the first `type:*` label won, so adding `type:epic` to a parent with work (M4, #15) would have closed it without running that work.
- **`fact:needs-human` (26 Nov 2026, revised 27 Nov 2026):** set by the factory on an issue it will not touch again until a person acts (a gate, a blocker closed without completing, or a run end the scheduler does not retry, below). Only a person clears it: answering the gate with `fact gate`, removing the label, or starting the task with `fact run`, which removes it first. The scheduler skips such issues. `fact:running` is retired. Details in `12-integrations.md`.
- **The label is the hold (27 Nov 2026):** a task labelled `fact:ready` without `fact:needs-human`, whose ancestors are ready, whose dependencies are done and with no run in progress, is one the scheduler starts; anything the scheduler will not start for a reason only a person can lift carries `fact:needs-human`. Run ends that hold the task add the label, keep `fact:ready`, comment why and how to release it, and send a `task_held` notification: `stopped`, `needs_human`, `pr_opened`, `closed` (its PR closed without merging), and the `failed` run that reaches `concurrency.max_failed_runs` in a row. A `failed` run below the cap holds nothing and is retried. Run history only counts failures in a row. Why: the scheduler used to hold such tasks through the runs table alone, so an issue still showed `fact:ready` and was missing from the scheduler preview while nothing would ever start it, and no one was told (a stopped run of #11 sat unnoticed overnight). File tasks have no labels and keep the run-history rule. Details in `08-planning.md` and `12-integrations.md`.
- **Task status (27 Nov 2026):** a task's status (`backlog`, `todo`, `in progress`, `in review`, `done`, `not planned`, `duplicate`) is shown in the tracker, on GitHub as the native issue status (public preview since 23 Nov 2026), on Linear as its workflow state. fact pushes it forward and never reads it: planning sets Backlog or Todo with `fact:planned` or `fact:ready`, a run start moves it to In progress and opened PRs to In review, closing sets Done, and nothing moves it back (a held or failed task has started, so it stays). Labels stay the trigger, the gate and the hold. Why: people see where work stands in GitHub's own views and filters (`status:`) as they would in Linear, at no risk to scheduling. The status cannot be the trigger: GitHub moves it on its own (assigning a person moves an issue to Todo, a linked draft PR to In progress), so approval would leak to every automation that writes it, and its fixed set has nothing for an issue held for a person. Single responsibility: planning owns Backlog and Todo, runs own In progress and In review; the scheduler sets no status. Details in `12-integrations.md`.
- **Configuration as code (26 Nov 2026):** all configuration of a project and its workflows is code in the project's repository (`.fact/`): project-wide settings in `.fact/project.yaml`, each workflow's settings (task types and complexities it serves, harness and model per stage, prompts, retry limits) beside it in `.fact/workflows/`. The UI shows it and edits it only through PRs. `fact.yaml` is deprecated: the project registry moves to the factory DB (registering a project is data, like creating a repository on GitHub), and process settings (paths, ports, URLs) become environment configuration (`.env` locally, deployment config when hosted). The routing table leaves `fact.yaml` for the workflow files.
- **Secrets (26 Nov 2026):** never in git. How secrets are managed (a secret store, per-project agent credentials when hosted) is designed in its own milestone, not yet scheduled (listed under M7 for now).
- **Plan approval belongs to the planner (26 Nov 2026):** planning happens before runs and is not part of workflows; how the `approve_plan` gate changes is decided with the planner (M6).
- **Stop, not drop, for runs (26 Nov 2026):** runs are stopped (`stopped` outcome, `POST /runs/{id}/stop`); tasks are dropped, only in the tracker. Renamed in M3 before the API snapshot exists, since nothing is released yet. A run refuses to start while its task has an active run (409).
- **Name and domains (26 Nov 2026):** the product is *fact* everywhere inside it. The domain is `sofact.dev`: the landing page on the root, the app at `app.sofact.dev`, the API at `api.sofact.dev` (when hosted). The landing page may be hosted apart from the app.
- **The UI is the product (26 Nov 2026):** everything a person does happens in the web UI over the API. The CLI keeps only `fact dev` and `fact use`; every other command is deleted by the ticket that ships its UI replacement.
- **Scheduler always on (26 Nov 2026, reconciled 27 Nov 2026):** the scheduler is not a switch people use; the factory's point is that it runs. A project can be paused (a project setting, out of the way), which stops new runs of that project. Replaces `concurrency.scheduler_enabled`. Outside dev there is no switch: the outside trigger (a cron or a webhook calling `POST /scheduler/tick`) decides when ticks run. In dev, `fact scheduler on|off` stays as a developer convenience over the API's in-process loop, on at every API start.
- **Who started a run (26 Nov 2026):** each run records `started_by`: a person or the scheduler (later a `@sofact-dev` comment). Notifications go to the whole project for now; later to the person who started the run or is assigned.
- **Assets in git LFS:** images and other binary assets are stored with git LFS (`.gitattributes`); the logo lives in `web/public/brand/`.
- **M4 UI (26 Nov 2026):** no auth in M4; dark mode waits for user accounts (it is a user preference); TypeScript strict everywhere, API types generated from FastAPI's OpenAPI; every notification also fires a desktop notification; `fact dev` always starts Vite, and `fact use` builds the UI for a pinned factory. Details in `11-ui-and-notifications.md`.
- **Task priority (26 Nov 2026):** four levels, `urgent`, `high`, `medium`, `low`; none means `medium`. On GitHub a `priority:*` label, in a task file a `priority:` field, on Linear its native priority. The scheduler orders each project's ready tasks by effective priority (inherited from the tasks they block), then dependency depth, then id. Projects are ordered independently: they will run on separate runner pools and do not compete; the tick still goes round-robin across projects, each filling only its own pool, and inheritance stays within a project. Several `priority:*` labels: the highest wins. The planner asks for a priority and suggests one. Order only: no preemption, no exception to caps or the usage reserve; `fact run` starts anything by hand. No priority defaults by type. Details in `08-planning.md`.
- **Workflow design principles (27 Nov 2026):** workflows do no unnecessary work and add no artificial waiting: events over polling, short poll intervals, and state read from its single source of truth (GitHub for a PR) instead of copied or predicted. A workflow stays a simple graph of states that loop over the same steps, not special-case paths. Why: each extra step costs agent time, CI rounds and wall time, and each special path is another edge case to test and another state for the UI, stop and resume to handle; loops over a few states move cleanly from one state to the next. Example: a first design merged `origin/main` into the task branch before opening the PR and again after resolving, whenever `main` had moved. It was rejected as extra commits, pushes and CI rounds for a question GitHub already answers (`mergeable_state`). Runs now merge the base only when GitHub says the PR cannot merge, through the existing CI loop (`docs/decisions-2.md`, 27 Nov 2026). Details in `06-workflow-authoring.md`.
- **Runs survive a restart (27 Nov 2026):** workflows, and the activities they call, never depend on in-process state for correctness or coordination: no module- or instance-level locks, caches or registries keyed by run or workflow, and no assumption that a retry lands on the same process. What a run needs lives in Temporal (workflow state, history, heartbeat details), the database or API, the artifact store, or on disk where it can be found again (git's own state in the worktree). Coordination uses Temporal's guarantees: heartbeats and heartbeat timeouts so an abandoned attempt is detected and cancelled, `WAIT_CANCELLED` cancellation for activities that touch the workspace, idempotent activities that detect and resume partial work (a merge left in progress), and the external system's own locks (git `index.lock`). A process-local cache is allowed only if losing it changes nothing but speed. Why: a worker restart or a retry on another process must not break a run in flight. Example: a first `sync_base` kept a per-run `defaultdict(asyncio.Lock)` (`_run_locks`) so a retried attempt would not run git in the worktree of a timed-out one. It protected only within one process, was lost on restart, leaked one entry per run, and caused its own bug: a retry queued behind the lock sent no heartbeat and could time out. It was replaced by heartbeats, `WAIT_CANCELLED` and git's own lock. Details in `06-workflow-authoring.md`.
- **Framework and project boundary (27 Nov 2026):**
  - **The framework owns the run lifecycle.** It records the run's start and end, reports to the task source, handles stop, sends the notifications every run sends, collects each step's data (time, wait, tokens, cost, logs, transcript), posts the cost comment and applies the guardrails.
  - **The project owns the graph.** It decides which steps run, in what order and depending on what, with no constraint from the framework. A step may send its own notifications through the framework's notification step.
  - **Projects may define their own step types**, as well as using the factory's.
  - **Activity mechanics belong to the framework.** Timeouts, heartbeats, retries and cancellation are never something a project sets.
  - **One kind of workflow.** There are no separate workflow classes. Steps record what a run produced as typed outputs (a change set, tasks, a deployment), and a run that finds nothing to do produces none. A workspace is a resource that a step requests and the framework releases, so a workflow without one is valid. fact orchestrates external tools and records what they did; it never reimplements them (a deploy stays a GitHub Action or a project script, which a step triggers and watches).
  - **A project's own step types run outside the factory.** The project declares the step (its name, its typed input and output, and a command such as `uv run .fact/steps/deploy.py`). One generic framework activity runs that command in the run's runner, sends the input as JSON and reads the result as JSON. Project code never runs inside a factory process, so it uses the project's own environment, can be written in any language and gets only the runner's secrets.
  - **The orchestrator does as little as possible.** The factory process mostly orchestrates. Runners are self-contained on the infrastructure they run on, so the design still holds with thousands of them.
  - **Versions.** A run's version is the SDK version plus the project config version, a git version of everything under `.fact/` (workflows, prompts, config); that version is also what config benchmarks compare later. The worker refuses to load a project workflow whose SDK version it cannot run. Until 1.0 that check is the only compatibility machinery: no shims.
  - **Outcomes are generic.** A run ends `succeeded`, `nothing_to_do`, `failed`, `needs_human` or `stopped`. `pr_opened`, `merged` and `closed` become states of the change set output.
  - **Split of concerns.** The framework owns activity mechanics, step records and usage, payload limits, gate ids and their notifications, run-end notifications, workspace mechanics, push and merge mechanics, the cost comment, stop and handoff, usage pauses, budgets and versioning. The project owns its software development process and its graph: steps, order, loops, prompts, commands, answer schemas, fix counts, `max_duration`, gate placement, harness and model per stage, merge policy, and its PR description (template and prompts).
  - **Several machines: the seam only.** Steps reach a workspace through its handle, which names the queue its runner polls; no workflow code assumes one machine. Running across several workers, workspace recovery and several workspaces per run are M7 (`tasks/backlog.md`).
  - **SDK shape.** The run holds the framework's state: the default workspace, prepared the first time a step needs it, and the change set. Steps find that state themselves, so a project never passes it around. Stages are class attributes of the workflow (`implement = Agent("Implement", prompt="implement")`), and the stage manifest is derived from them. Composite library steps (`Checks`, `ChangeSet`) carry the framework's opinions. A step that does not pass ends the run with the matching outcome unless the step is `required=False` or the project handles its result. Project code never sees Temporal options or exceptions.
  - **Factory secrets never reach a runner.** Control workers are stateless, scale horizontally and hold the factory's credentials (the GitHub App key, the API). They run the GitHub, tracker, notification and bookkeeping activities. Runners do the work on the workspace. A long wait is a workflow timer plus a short check on each poll, never one activity held for the whole wait.
  - **Version format.** The SDK is versioned with semver, starting at 0.1.0. The project config version is the git tree hash of `.fact/`, so commits outside `.fact/` leave it unchanged; the run also records the home SHA it loaded from. A run's activities run on workers of the same factory build as its workflow.
  - **New config versions load without a restart.** When `.fact/` changes on a project's default branch, the running worker loads the new config version as one more Temporal worker in the same process, and new runs go to it. The old version keeps serving its runs until the last one ends. A change to the SDK or the factory still needs a restart.
  - **Semver, 0.x rules.** Before 1.0, a breaking change bumps the minor version (0.1 to 0.2) and a compatible change bumps the patch. A project declares the range of versions it works with (`~0.1`).
  - **One version for fact and the SDK**, in the root `pyproject.toml`, starting at 0.1.0. A change that affects projects moves it: the public `fact.sdk` API, the step protocol, the `.fact/project.yaml` schema or the prompt variables. A committed SDK API snapshot works like `api/openapi.json`: a test fails when the snapshot changes and the version does not, or when a breaking change moves only the patch. No git tags before 1.0: until then, a project's CI checks against fact's `main`.
  - **Checking a project's workflows.** `python -m fact.sdk.check .fact` checks that:
    - the workflows import, and import nothing they may not;
    - the SDK range matches;
    - the stage manifest can be derived;
    - the prompts and scripts they name exist;
    - the step declarations are valid.

    It runs in three places: in the project's CI, through a reusable GitHub Action (or the same `uvx` command); inside a run whose change touches `.fact/`, in the workspace and against the fact version that change targets (in fact's own repository, the workspace's own SDK); and when the worker loads a version.
  - **An incompatible workflow is refused, never fatal.** When a project's version fails the check, the worker refuses to run it (an error is logged and an `error` notification sent) and keeps serving every other project and version. A refused project's tasks are not started (scheduler `Hold` `incompatible`).
  - **Composite steps are made of slots.** Each composite library step is built from named slots with framework defaults, and a project can replace any slot with a step type of its own. For example, `ChangeSet`'s `describe` slot builds the PR title and body; a project that replaces it can write its PR description with any logic it likes. The framework still pushes and opens the PRs, and adds its footer and the cost comment. To be tried in practice.
  - **Project workflows import only `fact.sdk`.** That is one public module, which also provides the workflow decorator. Project workflows never import `temporalio` or `fact.core`, and never call `execute_activity`. An AST check enforces this. A second check, over `worker/` and `sdk/`, catches in-process run state.
  - **The step protocol.** A Script step reads its input from the JSON file at `FACT_INPUT`, writes its JSON result to `FACT_RESULT`, and may append outputs, notifications and progress to the JSON-lines file at `FACT_EVENTS`. stdout and stderr are its log. Exit code 0 means passed, 2 means `needs_human`, and anything else means failed.
  - **Built by the factory, before the M4 UI**, as an epic of sub-issues run one at a time in dependency order: activity specs and calls; lifecycle and outputs; stages as attributes and composite steps; project step types; versioning; the check; config versions without a restart. AGENTS.md is updated by each sub-issue as it lands. Details in `06-workflow-authoring.md` (The workflow SDK) and `09-runners-and-harnesses.md`.
  - Why: agents write most workflow code, and an agent that has to wire the lifecycle by hand can skip part of it or get it wrong (#61: a workspace activity awaited with no heartbeat).
- **Factory settings and project config (27 Nov 2026):** two kinds of config that never share a file. `fact.yaml` holds factory settings only (the deployment: machine and processes, factory concurrency cap, scheduler policy, accounts, project registry) and is the `fact dev` config in the factory repo; a deployment overrides it. Everything about how a project's tasks run is project config in its `.fact/project.yaml`: routing, step limits and its own concurrency cap included, and fact's own included. Step limits have defaults in the SDK's code that a project overrides. Why: a project owns its config in its own source control, and fact being its own project must not mix the two. Details in `05-domain-model.md` and `13-storage-and-stack.md`.
- **Concurrency counts compute (27 Nov 2026):** the factory cap and a project's cap count concurrent runs (queued or running) only; waiting runs hold no slot, and a resumed run queues for a slot. Why: the caps regulate workers and spend, which a run waiting on a person does not use. Built later, with queue-based processing (M5.3, `tasks/backlog.md`); v0 counts waiting runs too. Details in `10-observability.md`.
- **Following a ref (27 Nov 2026):** `fact dev --follow <ref>` upgrades when the ref moves and no run is active; `--on version` upgrades only when the fact version changes. Details in `06-workflow-authoring.md`.
- **People answer on GitHub (27 Nov 2026):** a PR's review follows GitHub's flow: an approval on the head merges it once CI is green (a reviewed merge, whatever `auto_merge` says), and each review requesting changes gets one `review_reply` session that replies to its comments and either sends the run back through the whole chain or only replies, then re-requests review. Each PR merges on its own; the run waits for all. A blocked agent with a `question` asks it on the issue, and an `answer` session reads the replies that mention the GitHub App, `@sofact-dev` (`continue`, `ask`, `stop`); exhausted loops end `needs_human` with no gate. Multi-repository review is left open. Details in `07-reference-workflow.md`. Why: people already review on GitHub; answering through the CLI was the gap.
- **M5 Cloud (27 Nov 2026):** the control plane runs hosted on Railway: the API (serving the UI), the control worker (workflow code and control activities), the factory database, Temporal (self-hosted, not Temporal Cloud) and the artifact store. The runner worker, which prepares workspaces and runs agents and checks, stays on your PC. The deployment is reachable on the public internet, so every route is authenticated, and a test fails on any route that is not. Local `fact dev` keeps working unchanged, with no cloud at all. GCP (too heavy and costly for now), a single VPS and Temporal Cloud (about $100 a month) were rejected. Deploying `main` from CI, and upgrades that wait for or drain active runs, are stretch tasks, not required for M5. Once hosted, the GitHub App's webhook is on (part of M5). Cloud secrets are Railway service variables until the secret-store design. A project is registered in one factory at a time, managed by hand (no guard in code); the runner and the cloud run the same fact version, kept in step by hand. M5 is pre-planned before M4 is built and planned again once M4 ships: its issues stay `fact:planned`.
- **M5 control and runners (27 Nov 2026):** the control worker does no compute: workflow tasks and light I/O only, stateless, scaled by replicas. Runners do everything that touches a workspace (git, checks, agents, diffs, signals, transcripts). The GitHub App private key lives only in the cloud: a runner gets an installation token from the API, narrowed to the run's repositories and `contents: write`, only for an active run of its pool, and never through a Temporal payload; it uploads artifacts straight to storage through presigned URLs. A runner pool brings its own harness credentials (in M5, the local Claude Code login on your PC); other providers' keys come with other harnesses.
- **Auth on every route (27 Nov 2026):** deny by default. Each route declares one class: `user` (signed-in person), `runner` (runner token, only runner routes and its own runs), `service` (internal callers, their own token), `webhook` (GitHub's HMAC signature) or `public` (`/health` only). A test fails on a route with no class and on any route that answers without valid credentials. Local dev runs the same checks against a local provider (a token `fact dev` generates); auth is never switched off.
- **Webhooks wake, GitHub stays the state (27 Nov 2026):** deliveries are verified and deduplicated by delivery id; issue events trigger a tick, PR reviews, comments and check completions signal the waiting run to read GitHub now. Polling stays as a slow fallback so a lost delivery only delays. Local dev keeps short polling.
- **Mail (27 Nov 2026):** Resend sends fact's email: Supabase Auth's emails in M5, notification email once user accounts exist.
- **Queue technology (27 Nov 2026):** the run queue is a plain table in the factory database with a single dispatcher holding a Postgres advisory lock; not pgmq (no re-prioritizing), not Temporal task queue priority (coarse, the queue invisible), not a broker.
- **M5 data, runners and admin access (27 Nov 2026):** Supabase holds fact's database, Auth and Storage (chosen over Railway Postgres plus our own GitHub OAuth for its auth, storage and tooling; reached through its pooler in session mode). Temporal gets its own Railway Postgres: its data is the live state of open runs, kept 14 days after a run closes, never read for reporting, so it need not share fact's storage and is kept off Supabase's connection budget. Runners are Temporal workers polling over TLS with short-lived JWTs that fact's API issues from a runner token (Temporal's built-in authorizer, `worker` role), not a polling API we would build; a namespace per organization later. A run's runner activities stick to the machine holding its workspace. Usage limits move to the runner, which stops polling while its window is spent; the factory's usage gate goes. Admins reach the Temporal UI through Cloudflare Access, never publicly. Accounts are created only on the Supabase dashboard (sign-ups off), also after M5.2, until a sign-up flow ships. Details in `19-cloud.md`.
- **Run queue (27 Nov 2026, M5.3):** a slot covers compute, not the whole run: a run releases it before every wait and asks again with a `resume` entry when the wait ends. Resumes rank at least `high`, so only urgent work passes a run already under way; priority comes only from the tracker, with no manual reordering. Grants respect the factory cap, the project cap and the pool's live capacity. A waiting run keeps its workspace until `workspace.keep_while_waiting` (default `forever`). Details in `10-observability.md`.
- **Human actions:** fact needs a way to request and track actions only a person can do, such as downloading the GitHub App private key. In the backlog.
