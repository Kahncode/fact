# Domain model

A project is a set of repos, and a run works on all of them at once in one workspace, producing one change set of PRs.

**Terms.** A *project* is a factory concept: one product, with its workflows, triage rules and budgets. A *repository* is a GitHub repo. A project has one or more repositories, and a run can touch several of them, so every link the factory shows (branch, PR, CI run) belongs to one repository. Linear projects and GitHub Projects are only mapped to factory projects, never the same thing. A *task* is an issue (or task file) fact may run. A task's *priority* is `urgent`, `high`, `medium` or `low`; a task without one is `medium`. Its *effective priority* is the highest of its own priority and the priorities of every ready task of the same project it blocks, directly or through other tasks (a task not ready yet does not raise it), so a blocker never waits behind work less urgent than what it holds up. Priority only orders which ready task starts next within a project; it never preempts a run or bypasses a cap or the usage reserve. A *parent issue* has sub-issues, which are its dependencies; an *epic* (`type:epic`) is a parent with no work of its own. Sub-issues and blocked-by links are different: see `08-planning.md`. A *notification* is a message the factory sends a person because something needs them (a gate, PRs that need review, a failed run) or is worth checking (a warning); routine progress never notifies. A notification is *read* once the person has seen it and *resolved* once what it asked for no longer applies (the gate was answered, the PRs merged or closed, the failed run was stopped or restarted); the factory resolves it, the person never has to. The *inbox* is the list of unresolved notifications. A notification is addressed to a project (everyone on it) for now; later to a person, such as the one who started the run. A run's *started by* is a person or the scheduler. An *upgrade* moves the running factory to a new pinned version. An upgrade is *pending* from the moment the followed ref moves until no run is active; while it is pending, the scheduler starts nothing. A run is *stopped* (decided 26 Nov 2026): it ends where it is, keeps its branch and PR and leaves a handoff note; a stopped run is never restarted, but a new run of the same task can start later and resumes from the note. A *workflow type* is made of steps, and a *run* executes one. A *step type* is a reusable kind of step, either from the factory's *step library* or one of the project's own; a *step* is one execution of a step type in a run, per attempt. *Lifecycle steps* are the steps the framework adds to every run, whatever its workflow (start, task reporting, stop and handoff, teardown, cost comment, run-end notification); the project's workflow decides every other step and their order. An *output* is something a run produced through its steps (a change set, tasks created in the tracker, a deployment); a run that found nothing to do has none. A task is *dropped* when it is closed without being done. A task has at most one active run at a time. Tasks are dropped only in the tracker, never by fact; a run whose task was closed while it ran finishes, and its change set then needs a human review (classify checks that the task is still open). *Factory settings* are what a deployment of fact decides: the machine and its processes, the factory's concurrency cap, scheduler policy, agent accounts and their usage reserve, and the registry of projects it serves; they live in `fact.yaml`, which in the factory repository is the `fact dev` config. *Project config* is what a project decides about how its tasks run: its repositories, task source, workflows and prompts, routing, step limits, its own concurrency cap and its merge policy; it lives in `.fact/` in the project's home repository, under the project's source control. fact is also a project, so its own project config is its `.fact/`, never `fact.yaml`. A run is *concurrent* while it is queued or running, using a worker and compute; a run waiting on a person or a usage limit is not concurrent and holds no slot. Concurrency caps count concurrent runs only.

| Entity | What it is | Key fields |
| --- | --- | --- |
| Project | A product the factory works on | name, repositories, mapped task source (GitHub repository or Linear team), workflow catalog, triage rules, preview deploy command, runner pool, budgets, merge policy, policies |
| Repository | One GitHub repo inside a project | URL, role (backend, mobile, web, infra), default branch, setup, test and build commands, merge order |
| Workflow type | A Python workflow class, one or more per project | name, stage manifest, worker version (factory git SHA) |
| Run | One Temporal workflow execution for one work item | workflow id `run-<ISSUE-KEY>-<n>`, project, issue, status, totals for time, cost and human touches |
| Step | One activity or gate inside a run, per attempt | kind (agent, shell, github, gate, notify), name (tells apart steps of one stage: the check or prompt), attempt, start, end, duration, wait time, tokens, cost, log and transcript refs, outputs |
| Workspace | The per-run folder | one git worktree per repo, all on branch `fact/<ISSUE-KEY>` |
| Change set | The PRs a run produces | one PR per touched repo, cross-linked, with a merge order |
| Runner pool | Where a run's sandbox lives: your PC, containers, GitHub runners, Daytona | kind, concurrency cap, secrets |
| Harness | Which coding agent runs an agent step | Claude Code, Codex, OpenCode, Pi; model; allowed tools; chosen per task or per step (see Choosing a harness and model) |

**How multi-repo works**

- The project config lists its repos; a run checks out a worktree of each repo it needs, side by side, so one agent can see the backend and the mobile app together.
- The agent sees one workspace folder with a short `WORKSPACE.md` describing the repos and how they relate.
- At PR time the factory opens one PR per repo that changed, links them to each other in their descriptions, and records a merge order (for example backend before mobile) that the UI shows.
