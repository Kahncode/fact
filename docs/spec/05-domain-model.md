# Domain model

A project is a set of repos, and a run works on all of them at once in one workspace, producing one change set of PRs.

**Terms.** A *project* is a factory concept: one product, with its workflows, triage rules and budgets. A *repository* is a GitHub repo. A project has one or more repositories, and a run can touch several of them, so every link the factory shows (branch, PR, CI run) belongs to one repository. Linear projects and GitHub Projects are only mapped to factory projects, never the same thing. A *task* is an issue (or task file) fact may run. A task's *status* is where it stands in the tracker's workflow: `backlog` (planned, not approved), `todo` (approved, not started), `in progress` (a run started; a run waiting on a person or held by fact is still in progress), `in review` (its change set is open for review), `done`, `not planned` or `duplicate`. The status is for people: fact never reads it to decide anything, it only moves it forward. Labels, not the status, approve, gate and hold work. Each task source maps the status onto its own (GitHub's native issue statuses, Linear's workflow states); a source without one ignores it. A task's *priority* is `urgent`, `high`, `medium` or `low`; a task without one is `medium`. Its *effective priority* is the highest of its own priority and the priorities of every ready task of the same project it blocks, directly or through other tasks (a task not ready yet does not raise it), so a blocker never waits behind work less urgent than what it holds up. Priority only orders which ready task starts next within a project; it never preempts a run or bypasses a cap or the usage reserve. A *parent issue* has sub-issues, which are its dependencies; an *epic* (`type:epic`) is a parent that holds other parents or a plan of work; the label is for people, and fact ignores it. A parent's *work type* is its `type:*` label other than `type:epic`: a parent with one has work of its own and runs once its sub-issues are closed, a parent without one is closed without a run. Sub-issues and blocked-by links are different: see `08-planning.md`. A *notification* is a message the factory sends a person because something needs them (a gate, PRs that need review, a failed run) or is worth checking (a warning); routine progress never notifies. A notification is *read* once the person has seen it and *resolved* once what it asked for no longer applies (the gate was answered, the PRs merged or closed, the failed run was stopped or restarted); the factory resolves it, the person never has to. The *inbox* is the list of unresolved notifications. A notification is addressed to a project (everyone on it) for now; later to a person, such as the one who started the run. A run's *started by* is a person or the scheduler. An *upgrade* moves the running factory to a new pinned version. An upgrade is *pending* from the moment the followed ref moves until no run is active; while it is pending, the scheduler starts nothing. A run is *stopped* (decided 26 Nov 2026): it ends where it is, keeps its branch and PR and leaves a handoff note; a stopped run is never restarted, but a new run of the same task can start later and resumes from the note. A *workflow type* is made of steps, and a *run* executes one. A *step type* is a reusable kind of step, either from the factory's *step library* or one of the project's own; a *step* is one execution of a step type in a run, per attempt. *Lifecycle steps* are the steps the framework adds to every run, whatever its workflow (start, task reporting, stop and handoff, teardown, cost comment, run-end notification); the project's workflow decides every other step and their order. An *output* is something a run produced through its steps (a change set, tasks created in the tracker, a deployment); a run that found nothing to do has none. A task is *dropped* when it is closed without being done. A task has at most one active run at a time. Tasks are dropped only in the tracker, never by fact; a run whose task was closed while it ran finishes, and its change set then needs a human review (classify checks that the task is still open). *Factory settings* are what a deployment of fact decides: the machine and its processes, the factory's concurrency cap, scheduler policy, agent accounts and their usage reserve, and the registry of projects it serves; they live in `fact.yaml`, which in the factory repository is the `fact dev` config. *Project config* is what a project decides about how its tasks run: its repositories, task source, workflows and prompts, routing, step limits, its own concurrency cap and its merge policy; it lives in `.fact/` in the project's home repository, under the project's source control. fact is also a project, so its own project config is its `.fact/`, never `fact.yaml`. A run is *concurrent* while it is queued or running, using a worker and compute; a run waiting on a person or a usage limit is not concurrent and holds no slot. Concurrency caps count concurrent runs only. A PR is *approved* when it has an approving review on its head commit; an approval on an older commit does not count. An approved PR merged by fact is a *reviewed merge*, never an auto-merge, which is fact merging with no person's review. A *review round* is one review that requests changes, handled as a whole: fact replies to its comments, changes the code or not, and asks for a review again. Each PR of a change set is reviewed and merged on its own; the run ends once every PR is merged or closed. A *question* is what a blocked agent needs from a person; it is asked *on the task* (a comment on the issue) and the conversation there answers its gate. A *turn* is one call to the model in an agent session: one response, with the tool calls it asks for; running those tools is not a turn. A *session* is an agent step's conversation with its harness, from its prompt to its last answer; a session can stop and be woken again in the same step (Claude Code wakes it when a background task it started finishes), and its turns, tokens and cost count over the whole session. A session's *peak context* is the input of its largest turn: how much of the context window it used.

| Entity | What it is | Key fields |
| --- | --- | --- |
| Project | A product the factory works on | name, repositories, mapped task source (GitHub repository or Linear team), workflow catalog, triage rules, preview deploy command, runner pool, budgets, merge policy, policies |
| Repository | One GitHub repo inside a project | URL, role (backend, mobile, web, infra), default branch, setup, test and build commands, merge order |
| Workflow type | A Python workflow class, one or more per project | name, stage manifest, worker version (factory git SHA) |
| Run | One Temporal workflow execution for one work item | workflow id `run-<ISSUE-KEY>-<n>`, project, issue, status, totals for time, cost and human touches |
| Step | One activity or gate inside a run, per attempt | kind (agent, shell, github, gate, notify), name (tells apart steps of one stage: the check or prompt), attempt, start, end, duration, wait time, tokens, cost, log and transcript refs, outputs |
| Workspace | The per-run folder | one git worktree per repo, all on branch `fact/<ISSUE-KEY>` |
| Change set | The PRs a run produces | one PR per touched repo, cross-linked, with a merge order |
| Runner pool | Where a run's sandbox lives: your PC, containers, GitHub runners, Daytona | kind, concurrency cap, secrets |
| Harness | Which coding agent runs an agent step | Claude Code, Codex, OpenCode, Pi; model; allowed tools; chosen per task or per step (see Choosing a harness and model) |

**How multi-repo works**

- The project config lists its repos; a run checks out a worktree of each repo it needs, side by side, so one agent can see the backend and the mobile app together.
- The agent sees one workspace folder with a short `WORKSPACE.md` describing the repos and how they relate.
- At PR time the factory opens one PR per repo that changed, links them to each other in their descriptions, and records a merge order (for example backend before mobile) that the UI shows.
