# Software factory UX: Warp Factories and Factory (research, 26 Nov 2026)

Read from public docs only (no account, no login-gated pages). Used to design fact's web UI (`docs/spec/11-ui-and-notifications.md`). Unverified: actual visuals (colors, fonts), Factory's in-app Analytics and inbox pages, keyboard shortcuts beyond Factory's changelog.

## Warp Factories (docs.warp.dev/factories)

**Hierarchy and navigation.** Team → factory → repositories, workers, automations. A factory is one definition over a set of repositories that ship together; there is no project concept below it. Team-wide sidebar: Home (personal), New Chat, Runs, MCPs and apps, Secrets, Integrations, then the list of factories. Per factory: Dashboard, Blueprint, Workers, Automations (Webhooks tab), Scorers, Self-improvement, Benchmarks, Factory definition, Settings.

**Home (the inbox).** Defaults to the filter "Waiting on you"; other filters Active, Complete, Blocked, Failed; search over runs; grouped Today / This week / All time; items grouped by work item; opening an item shows a side pane and marks it read without resolving it. Item kinds: Asked question, Answered question (info), Spec review, PR review, Blocked, Failed. Items clear on their own (a review submitted, the PR merged or closed, the question answered); Mark as resolved by hand, with Undo. Results go back to the source tool (Slack thread, Linear ticket, GitHub PR); no email or push documented.

**Run page.** Timeline, cost (including child runs, split across the PRs it produced) and child runs grouped under their parent; actions: view the worker session, stop, score, add to a benchmark. No chat input on run pages; the worker session takes instructions while the sandbox lives and becomes a transcript afterwards. Session content: prompt, plan, task list, decisions, commands, logs, terminal output, artifacts, diffs, environment. Artifact types: plan, pull request, screenshot, file, external reference.

**Blueprint.** The workflow diagram; selecting a stage shows its worker and instructions, selecting a transition shows its condition. Loops are transitions (review sends findings back to implementation; a plan gate with changes requested loops back to planning). Gates ask a question and wait for the answer.

**Factory definition as code.** `factory.yaml` plus `workers/<name>/worker.md`, `automations/<name>/automation.md`, `scorers/<name>/scorer.md` (Markdown body = prompt or rubric, YAML front matter = config), `runners/*.yaml`, `skills/*/SKILL.md`, `benchmarks/<suite>/`. Published JSON Schemas, a validator and a PR check; edits go through a branch and a PR; a run keeps the definition it started with. Definitions hosted by Warp (editable in the app), on GitHub (read-only in the app) or API-only.

**Settings per factory.** Identity (name, avatar, handle), repositories, PR authorship (worker or run creator), analysis model, runners, integrations, deletion.

**Dashboard metrics.** Total runs (by agent, status, source, model); PRs opened; PRs merged; Autonomy (merged PRs with no human code push); PR cycle time (median, per stage: kickoff → PR, first review, merge); Cost per PR (median; compute, platform, inference; by PR size S/M/L/XL at 100/500/1,000 changed lines); most expensive PRs; opened vs merged chart; run breakdown; Scorer cards; newest self-improvement PRs.

**Scorers, self-improvement, benchmarks.** Scorers: LLM judge per run (instructions, model, classifications with scores, pass threshold, sample rate). Self-improvement: follow-up runs open PRs on the factory definition, each listing the regressions it addresses. Benchmarks: suites of tasks replayed against setups (branches of the definition), with repetitions, scorers, cost, duration, and a recommendation (best, most efficient, cheapest); any finished run can be added to a suite.

## Factory (docs.factory.com)

**Hierarchy.** Organization (with sub-organizations, groups, roles Owner / Manager / member), agent profiles (service account, compute, repositories, credentials, default model), projects (a git root with `.factory/`), folders, users. Settings layer Org > Runtime > Folder > Project > User > built-in; org "hard controls" cap what lower levels may choose, other settings take the most local value.

**App.** Sidebar: New session, sessions list with filters, Code Review, Automations, Mission Control, Workstreams, Wiki, Analytics, Settings. A session shows the transcript (tool rows, a focus mode folding runs of tool calls into one summary row, subagent rows, question cards with why it asks) beside a right pane with Changes, Files, Terminal and previews (documents, PDFs, live sites, full diffs with inline comments). Workstreams group agents as "Waiting on you", "Working", "Idle".

**Code Review.** Inbox tabs are saved GitHub-syntax searches (up to 20); actions Fix (conflicts, failing checks, review comments) and Auto-fix and Auto-merge switches per PR.

**Automations.** List (title with status and alert icon, owner, trigger, runs on), detail with a 7-day success rate and an events feed (runs, alerts, deliveries); statuses Active, Paused, Degraded, Failed; automatic pauses with a reason (repeated failures, missed runs, capacity).

**Attention.** Desktop notification sounds while the app is in the background; email for automation alerts (first failure at once, then a daily digest); usage alerts at 80% and 100% to owners and managers; Slack, Linear, Jira, Teams delegations reply in the thread or ticket.

**Shortcuts.** Cmd/Ctrl+K command palette with category tabs and ranked results (sessions by title and by transcript text, actions); Cmd+F find in page; settings search matches row descriptions.

**Analytics (from the API).** Credits per day by model, user and source; sessions (count, credits, duration, primary intent, linked issues and PRs); spend by the user who triggered a run; tool calls, MCP, skills, slash commands and hooks usage; autonomy ratio (avg, p50, p90); user turns per session; DAU/WAU/MAU by client; files created and edited by language; commits and PRs created; PR size, state, open-to-merge times and attribution (sessions, credits, contributors); tickets and projects with story points; usage windows (five-hour, weekly, monthly: used percent and reset time) with alert thresholds and credit limits per org, group and user.

## Warp Factories, seen in the app (26 Nov 2026)

Looked at with a real account and one finished run (Home, run page, worker session, Blueprint, Dashboard, Runs, Settings, Scorers, Self-improvement, Benchmarks, Factory definition). Screenshots, numbered, are in `docs/research/warp-factories/`.

- **Home**: status chips with counts (Waiting on you, Active, Complete, Blocked, Failed), search, rows grouped by day with chips for the PR, issue and repository. Opening a row opens a side pane with the run's conversation ending in a PR card ("PR is ready for your review", View PR), and lowers the unread count; "Mark as resolved" appears on hover.
- **Run page**: mostly the orchestrator's narration ("Worked for 16s ›" collapsed groups between messages), a follow-up box at the bottom (steering), an Artifacts tab (PRs with state) and a Metadata tab: environment, runner, run id (copy), trigger ("GitHub issue labeled"), run time, created, source, harness, model, usage in USD.
- **Run timeline** (toggle above the page): a time axis with a range slider, a *Stages* row of coloured segments, an *Automations* row with trigger events, and one lane per agent (orchestrator, researcher, task worker) with bars; hovering a stage shows "Work / Implement 5:34–5:44 PM · Jump to stage" and jumps the transcript there.
- **Worker session**: opens in a right split pane with a stage switcher; the agent's messages in full, tool activity folded into "Worked for 7s ›", which expands to "Ran 2 commands ›", "Reasoned for 2s ›". A subagent shows as "Launched 1 worker › task-worker: <its task>" with a status tick and its stage rows ("Work / Implement, completed in 9 min 53 s").
- **Blueprint**: a vertical graph with nested stages (a "work" stage holding triage, spec, implement, review) and 22 transitions drawn as orthogonal edges; hard to read. Useful bits: run count on every node, an Overview list of stages and transitions, a Runs tab, and a code view toggle.
- **Dashboard**: Productivity (human interactions per PR, median cycle time split kickoff → PR, PR → first human review, first human review → merge, kickoff → merge, shown "not measured" until data exists; PRs opened vs merged; total runs by worker type), Spending (cost per PR split compute, platform, inference; most expensive PRs; spend by source; spend by user), Scorers.
- **Runs list**: filter chips (mine, running, complete, failed, blocked, cancelled, background), compact rows with a status icon carrying the child-run count, artifact chips, the starter's avatar and the time.
- **Settings** sections: General info (name, avatar, foreman handle, PR author: worker or run creator, who can send follow-ups), Worker defaults, Scorer defaults, Benchmarking, Factory integrations, Factory repo, Runners, Access, Danger zone. A credit meter sits in the sidebar footer.

- **Scorers** (screenshots 11–15): six default LLM judges (Verbosity, Task Compliance, Stage Transition Compliance, Procedure Compliance, Efficiency on the orchestrator and task worker; Code Quality on the implement stage). A scorer has a scope (agents or blueprint stages), judge instructions (a rubric), a judge model, resources (runner, secrets, MCPs, inherited from worker defaults), classifications each with a score from 0 to 1 and a description (Code Quality: approve 1, insufficient_evidence 0.5, block 0.2), a pass threshold, a sample rate (default 10% of eligible stage executions, 0% pauses it) and a switch feeding self-improvement. Its page shows all-time scorer cost, a 30-day pass-rate and daily-cost trend, and its scoring runs; "Score past runs" scores a date range at a chosen sampling rate (runs younger than 30 minutes are skipped while evidence settles). Dashboard › Scorers shows one card per scorer.
- **Self-improvement** (16–18): collects scorer failures per evaluation target (an agent, a stage or a task); every 2 hours checks each target against a shared threshold (default 10 failures per target, or the oldest pending failure exceeding an age limit); analyses common failure patterns of eligible targets and, only if they are repeatable and significant, opens a PR on the factory definition; a randomly chosen team admin reviews it, nothing merges automatically. Configured with a model, runner, threshold, reviewers, the scorers that feed it and free-text instructions. "Run now" stays disabled until some target is eligible.
- **Benchmarks** (19–22): a suite has a name, description, scope (a worker or a stage), tasks and a built-in correctness scorer (judge model, runner). A task is made from a previous run (searchable list) or from scratch; adding one starts a background agent job that turns the run into a replayable task, and the suite is written to the definition (`benchmarks/<suite>/suite.yaml`). Running a suite compares setups (definition branches) with repetitions and scorers. Seen (28): the job took about 4 minutes and produced a change to review on a branch (`task/<id>/<slug>`): `suite.yaml` lists the task, and `tasks/<slug>.yaml` holds a title, a prompt rewritten from the run (the request, its scope, what to validate, plus a *contamination guard*: do not look up the already-shipped implementation in GitHub, branches or PRs), `successCriteria` as a checklist, and the pinned base commit. Approve & merge adds it to the definition. Not tried: running the suite (it needs the merge), and Score past runs, whose preview request (`POST …/scorers/<id>/backfill/preview`) never returned on two tries, perhaps because no run had finished long enough before.
- **Factory definition** (26): one `factory.yaml` (schema version, repositories, worker defaults, the blueprint: stages with description, worker, inputs, outputs, prompt file, and transitions `to: - stage: X, when: <prose condition>`), plus folders for automations, benchmarks, runners, scorers and skills; edited in the app on a branch, with Save committing.
- **Automations** (25): a table (automation, trigger, last run, enabled) of GitHub event triggers, plus suggested ones by category (stale PR follow-up, flaky tests, dependency audit, vulnerabilities, reviewer assignment, CI auto-fix).
- **Workers** (24): cards for the foreman, researcher and task worker, each with its role.

**Samuel's read (26 Nov 2026):** too chat-first; fact wants much less chat. Warp's design follows its agent model: a long-lived foreman converses with the requester and orchestrates every stage, dispatching workers, so the run page is that conversation. Stage transitions are prose conditions judged by the model, not code; there is no code-defined workflow and no auto-merge (merging stays with people). fact keeps its first approach: a structured run page (graph, timeline, step panel), workflows as code, auto-merge by classification. Worth harvesting later: scoring, self-improvement and benchmarks (already v0.2 in `docs/spec/15-milestones.md`, ideas in `tasks/backlog.md`). Their UX is input to validate together, not a model to copy.

Take: the timeline (stages row, lanes, jump to stage), the folded "Worked for…" transcript groups, opening a subagent in a split pane, the metadata block, chips with counts. Avoid: a run page that is only the orchestrator's chat, and a nested vertical graph with every transition drawn; fact keeps its left-to-right stage graph with loops as back-arrows.

## What fact borrows

- An inbox that opens on "Waiting on you", grouped by day and by run, where items resolve on their own and opening marks them read (fact's notification read/resolved split).
- GitHub-like project hierarchy with settings layered org > project > user later (Factory), project-scoped tabs.
- The run page as a timeline with cost, plus the workflow graph with loops as transitions (Warp's Blueprint).
- Definition edits through PRs, runs keeping the definition they started with (already fact's pinned workflows).
- Insights ideas: see `tasks/backlog.md`, Insights.
