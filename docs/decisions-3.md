## Decisions

### [2026-11-28 10:30] `fact cleanup` removes drained versions and old runs' files; `fact reset` wipes the factory

**What:** #137. `fact cleanup` (`@cli/src/fact/cli/cleanup.py`) removes the pins, Temporal versions and generation records of generations that are not the newest, have no live worker and none of whose versions Temporal reports current, ramping or `DRAINING`, plus `.trash-` leftovers, exited processes' records and stale worktrees (`git worktree prune`). `--older-than` deletes `artifacts/runs/<run_id>/` and `step-logs/<run_id>/` of finished runs ended before the cutoff, keeping every row. `fact dev` sets the namespace retention (`temporal.retention_days`, 30) through `UpdateNamespace` once Temporal is up. `fact reset` deletes the factory's data under `data_dir`. All print `removed`/`would remove`/`kept` with why; `--dry-run` changes nothing.
**Why:** old pins and drained versions pile up with every upgrade (`docs/spec/14-dogfooding-and-safety.md`, Disk cleanup). Safety comes first since it runs at any time: while Temporal cannot be asked every older generation is kept; a version Temporal refuses to delete keeps its whole generation (pins and record), so the next cleanup retries it rather than leaving a version whose pin is gone; Temporal refuses to delete a version while a stopped worker still counts as its poller (about five minutes by default), so a cleanup right after a generation drains keeps it once. A pin no generation names is kept for an hour, since `fact use` builds a pin before writing `current` and a starting worker clones its project pins before recording them. Process records are touched only while `fact dev` is stopped: a running one stops everything when a child's record disappears. Retention reads the database directly so it works without the API; a run is old only when `finished` with an `ended_at`. `temporal server start-dev` has no retention flag, hence the RPC. `fact reset` also refuses while a recorded process is alive (`fact dev` killed, its Temporal still holding `temporal.db`). Sandbox images, containers and volumes (in the spec) are not built yet, so cleanup does not handle them.

### [2026-11-28 14:00] Migrations are checked additive from source; a breaking upgrade restarts the open runs

**What:** #138 (c02324f, beedc89). `@core/src/fact/core/migration_rules.py` reads migration modules with `ast`, never importing them, and flags drops, renames, `alter_column`, new constraints and NOT NULL `add_column`s without a `server_default`; `@core/tests/test_migrations_additive.py` fails on one that does not set `breaking = True` (`usage_detail`, which makes `steps.cost_usd` nullable, is marked). The follower prepares a new pin without making it current and compares the migrations between the two heads (`breaking_between`); a breaking one (or an old head that is not an ancestor of the new) hands over to `BreakingUpgrade` (`@cli/src/fact/cli/breaking.py`), a restarter moving through `stopping`, `upgrading` and `restarting`, each phase written to `<data_dir>/run/upgrade.json`. The open runs are listed again once the recorded ones ended, so a run a scheduler tick in flight started is stopped too; only runs that ended `stopped` are started again (manual start with `override_deps`).
**Why:** two worker generations share one database (`docs/spec/14-dogfooding-and-safety.md`, Upgrading while it runs). Reading source lets the CLI check another pin's migrations without importing its code; columns must be declared inline in `add_column` for the check to read them. Persisting each phase makes the upgrade resumable after a killed `fact dev`, and an unreachable API (it restarts mid-upgrade) is retried at the next check rather than crashing the follower. A run that will not stop keeps the upgrade waiting: forcing it stays a person's call (`fact stop --force`).

### [2026-11-28 18:00] Sandbox images are built when a version loads, from the workflow's choice

**What:** #145. `RunnerPoolConfig` takes `kind: docker` with `memory`, `cpus`, `pids`, `run_args` and `default_sandbox` (refused on `local`). `FactWorkflow.sandbox` and `sandbox_args` go into `WorkspaceSpec.sandbox`/`sandbox_args`; a workflow naming none sends `None`, which that version's `prepare_workspace` maps to its own pool's `default_sandbox` (each version's activities are built with it), so the default always comes from the checkout that built the images, never from the API's copy of `.fact/project.yaml`. A refusal's notification is deduplicated by project, home SHA and sandbox, not by its message (a failed build's output differs at each attempt). `load_project` reads the pinned checkout's `runner_pool` and, on `docker`, builds each named `.fact/sandboxes/<name>/` (`@worker/src/fact/worker/sandboxes.py`), keeping the name-to-tag map in `ProjectWorkflows.sandbox_images`. A refused version now also sends an `error` notification (new `NotificationKind.ERROR`, no run).
**Why:** a run must never build or choose its own image (`docs/spec/09-runners-and-harnesses.md`, `docker` pool). The worker builds from the version's own checkout, so the images always match the workflows loaded; the folder hash makes a rebuild free when nothing changed, and a lost map costs only `docker image inspect` calls. The spec says the run gets its tag in `WorkspaceSpec`; the task asked for the name, which the runner (next issue) maps to the tag in the worker process. Folders are checked before Docker is asked, so a missing folder is refused even without Docker; Docker not answering stops the worker, since no `docker` project could run. Tests build `FROM scratch` images so they need no network; they skip unless Docker runs Linux containers.

### [2026-11-28 22:00] DockerRunner: one hardened container per run, tokens by name only

**What:** #146. `DockerRunner` (`@worker/src/fact/worker/runners/docker.py`, `docker_cli.py`) runs a `docker` pool version's workspaces: one runner per version, built with its `sandbox_images`. Container `fact-run-<run_id>`, volume `fact-ws-<run_id>`, both labelled `fact.run=<run_id>`. Each command gets a `contents: read` token for the run's repositories as `GITHUB_TOKEN` (`GitHubApp.repositories_token(full_names, permissions)`, one token per installation, cached like the per-repository one); git reads it through a `credential.https://github.com.helper` in the container user's `~/.gitconfig`, which holds only the helper. Every value reaches the container as `docker exec --env NAME`, its value in the client's environment. A command runs under an `sh` wrapper that writes its pid to `/tmp/fact-exec-<uuid>.pid` and stays the group's leader; timeout or cancel kills the group from a second `docker exec`.
**Why:** `--env NAME=value` would put the token in the host's process list and `docker run --env` in the container's config; neither holds a value this way. Docker already makes each `docker exec` process the leader of its own process group, and `setsid` would fork (ending the exec early), so the wrapper only records the pid. The read token covers fact's own git calls in `prepare` and `fetch` too; the caller's `env` wins over it, so a later push can hand its write token the same way. All repositories of a run must be in one installation for one token; a run spanning two installations fails at `prepare` (not needed yet). The workspace activities that still read the clone from the host (`shell_step`'s `.fact/repo.yaml`, prompts) move onto `exec` in the next issue.

### [2026-11-28 23:30] Workspace git steps and the push go through `Runner.exec`

**What:** #147. `push_branch` (`@worker/src/fact/worker/activities/push.py`, `workspace` zone, stage `push`) is split out of `open_change_set`: it runs `git lfs push origin <branch>` then `git push --no-verify origin <branch>` through the runner, with a `contents: write` token for the run's repositories in those two commands' environment only (as `GITHUB_TOKEN`, which keeps `DockerRunner` from minting its read token, and as an `http.https://github.com/.extraHeader`). `open_change_set` stays in the control zone and reads the branch's head from GitHub (`GET /git/ref/heads/<branch>`), never the clone. `classify_signals`, `mark_task_done` (`TaskDoneActivities`) and `sync_base`'s fetch move to the `workspace` zone and run git through `fact.worker.workspace_git.WorkspaceGit`; `Runner.fetch` is gone.
**Why:** with the `docker` pool nothing may read, commit or push from the host (`docs/spec/09-runners-and-harnesses.md`, `docker` pool). One code path serves both pools: `LocalRunner` runs the same commands on the host. The header goes to the origin's push as before and works on the host, where no credential helper reads `GITHUB_TOKEN`. `git lfs push` is skipped where `git lfs` is not installed: nothing was cleaned into LFS there, so there is nothing to upload. `mark_task_done` no longer opens the clone's `.fact/project.yaml` or a `FileTaskSource` on it: only a file task has `Task.path`, and the file in `HEAD` must still name the task (`fact.core.tasks.task_file_id`), which keeps the old guard against a renumbered file. The spec still says the `local` pool's control worker pushes directly; the task asked for one path, so it pushes from the workspace zone too.
