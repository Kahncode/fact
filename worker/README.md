# fact-worker

Temporal workers and activities: runners (where a run's sandbox lives) and harnesses (which coding agent runs in it).

Task queue names, activity names and activity input models (`AgentStepInput`, `ShellStepInput`, `CheckResult`, `CriterionResult`, `OpenChangeSetInput`, `PostCostCommentInput`, `WaitForCIInput`, `MarkTaskDoneInput`, `RunStartedInput`, `RunFinishedInput`, `RunWaitingInput`, `GateOpenedInput`, `GateAnsweredInput`, `NotifyInput`, `WaitForReviewInput`, `ReviewEvent`, `CollectCommentsInput`, `Comment`, `PostRepliesInput`, `Reply`, `RequestReviewInput`, `HandoffInput`, `HandoffStep`, `SyncBaseInput`, and the `ReviewEventKind`, `CommentKind` and `MergeResult` literals) live in `fact.core.activity_contract`, so workflow code in `fact.sdk` never imports this package; the worker modules re-export the old names. `python -m fact.worker` builds every activity once (`factory_activities`) and registers each on the queue of its spec's zone (`activity_workers.py`, `by_zone`, which refuses an activity with no `ActivitySpec`): `agent_step`, `shell_step`, `sync_base` and `teardown_workspace` (zone `workspace`) on the runner's queue, `sandbox` for `LocalRunner` (the queues only route work and cap nothing: how many runs go at once is the runner pool's `max_concurrent_runs`, enforced by the scheduler and `POST /runs/start`), everything else, `prepare_workspace` included, on `control`. Both activity workers exist once per loaded project, as that project's worker deployment version (below). Every activity worker runs `heartbeats.HeartbeatInterceptor`: it heartbeats each activity every 30 s while it runs, with the last details the activity handed to `heartbeats.report` (until then, its previous attempt's), so no activity heartbeats itself. Startup deletes a leftover `fact-scheduler` Schedule (see Scheduler below). It also runs one workflow worker per registered project; see below. Once the workers run, the main task waits in the keep-awake watch until the process is stopped (see Keep awake below).

## Workflow loading and versioning

`fact.worker.loader.load_project` pins a project to its home repository's default branch and imports its workflows (spec `docs/spec/06-workflow-authoring.md`, "How pinning is built"):

1. `default_branch_sha` asks the home repository's remote for the SHA of its `HEAD` (`git ls-remote`), so a renamed default branch is followed.
2. `pinned_checkout` reuses `pinned_dir/projects/<project>/<sha>` when its `HEAD` matches, otherwise clones the repository into `.<sha>.clone` beside it, checks the SHA out detached and renames it into place, so a clone cut short is never taken for a checkout.
3. `load_workflows` imports `.fact/workflows/*.py` in sorted order (`_`-prefixed files skipped) as `fact_workflows_<project>_<sha12>_<stem>`, through a meta path finder registered on `sys.meta_path`, so the workflow sandbox can re-import them by name. Two files mapping to the same module name are refused. It keeps the `FactWorkflow` subclasses defined in the module and decorated with `@workflow.defn`.

Any error is a `WorkflowLoadError` naming the project or file; `python -m fact.worker` logs `workflow_load_failed` and skips that project (a project with no workflows logs `no_workflows`). `factory_sha()` is the factory checkout's `HEAD`, or `unknown` when it is not a git checkout.

`fact.worker.deployments`: each loaded project gets a worker on task queue `wf-<project>` (`workflow_queue(project)` in `fact.core.activity_contract`), as version `<factory SHA[:12]>+<home SHA>` of deployment `wf-<project>`, with Worker Deployment Versioning and default behaviour `PINNED`. The project's `control` and workspace activity workers poll as the same version, so a run pinned to it runs its activities on workers of its own build: Temporal routes a pinned workflow's activities to its version when their queue belongs to that version, and one queue can belong to several projects' deployments (decision in `docs/decisions-2.md`). Two projects with one build id (one home repository at one SHA) fail startup with `DuplicateVersionError`: the SDK polls a queue once per build id in a process, so one of them would never get a worker. Once the workers start, `set_current_version` makes that version current (retried up to 10 times; startup fails if it cannot). `FactWorkflow.execute` passes the build id as `RunStartedInput.worker_version`, and `record_run_started` stores `worker_version` and `home_sha` on the run.

One process runs only the newest version: runs pinned to an older one wait after a restart on new code. `fact stop` is handled by the run's own version, so stop runs (and let them show `stopped`) before restarting; a run whose version no worker runs anymore, or started before M2-06, never processes the stop: delete its `<data_dir>/workspaces/<run_id>` by hand. This includes a run waiting for its PR to merge (`wait_for_review`): restarted on new code, it stalls after the merge. After merging, wait until the run shows `merged` (within about 60 s) before restarting. Side-by-side versions (`fact upgrade`) come later. `loader.sandbox_runner()` is the sandboxed runner every workflow worker (and the `Standard` tests, through `tests/standard_harness.py`) uses, with `fact`, `pydantic`, `pydantic_core` and `rich` passed through.

## Runners

`fact.worker.runners` has the `Runner` protocol and `LocalRunner` (see `docs/spec/09-runners-and-harnesses.md`). `LocalRunner(settings, remote_url, github=None, factory_root=REPO_ROOT, task_queue=SANDBOX_QUEUE)`: its handles name `task_queue`, where every workspace step of the run is sent (one machine: today's `sandbox`); `prepare` refuses a workspace inside `pinned_dir` or inside `factory_root` (the running factory checkout), so an agent never edits the code it runs on. `prepare` clones each repository in full (`git clone --no-checkout`, then `checkout -B` the task branch from `origin/<branch>` when it exists, else from `origin/<default_branch>`), so a workspace shares no git state, hooks included, with any other. With a `GitHubApp`, clones commit as its bot user (`fact[bot]`, from `bot_identity()`); without one, or if the lookup fails, as `commit_author_name`/`commit_author_email`. The runner keeps no lock or registry in memory: `prepare` and `teardown` hold the run lock `workspaces_dir/.<run_id>.lock`, an OS file lock (`filelock`, `runners/workspace_files.py`) that holds across worker processes and dies with its process, so overlapping attempts of one run take turns even on different workers. `prepare` returns the workspace an earlier attempt finished (`WORKSPACE.md`, written last and renamed into place, marks it; branches are read back from git), so a retry never tears down a workspace another attempt returned; otherwise it tears down any half-made folder of the run and starts over. The `prepare_workspace` activity heartbeats every 30 s and the workflow awaits it with `HEARTBEAT_TIMEOUT` and `WAIT_CANCELLED`, so a retry starts only once a stale attempt is cancelled or its worker is gone. `fetch(handle, full_name)` runs `git fetch --prune origin` in the workspace's clone. `teardown` runs the folder's `rmtree` in a thread. `fact.worker.runners.process` holds the subprocess helpers: `build_env` (the worker's environment plus what the caller passes), `spawn` (own process group; stderr merged and stdin closed unless asked otherwise) and `kill_tree`.

## Harnesses

`fact.worker.harnesses` holds the harness contract and its adapters.

- `HarnessRequest`: `prompt`, `cwd`, `model`, `allowed_tools`, `max_turns`, `permission_mode`, `output_schema` (JSON Schema for the final answer), `resume_session_id`, `env`.
- `HarnessResult`: `session_id`, `final_message`, `is_error`, `exit_code`, `stop_reason`, `num_turns` (over the whole session), `parts` (`SessionPart` per `result` message: `stop_reason`, `num_turns`, `cost_usd`), `usage` (`fact.core.types.Usage`), `structured_output` (the final answer matching `output_schema`, or None), `permission_denials` (`PermissionDenial`: `tool_name`, `tool_input`), `usage_windows` (`fact.core.claude_usage.ClaudeUsage`: the subscription windows the run reported), `rate_limited` (the usage limit refused the run).
- `Harness.run(request, transcript_path, on_message)` runs the agent to completion, writes every raw output line to `transcript_path` and calls `on_message` with each parsed message. Cancelling it kills the agent's process tree; the transcript written so far stays.

`ClaudeCodeHarness` runs `claude -p --output-format stream-json --verbose --permission-prompts none`, adding `--model`, `--max-turns`, `--permission-mode`, `--json-schema` (the schema as compact JSON), `--resume` and `--allowedTools` (one argument per rule, last) when set. `--permission-prompts none` keeps a headless session from ever waiting on an approval: a tool call that would prompt is denied and listed in the result's `permission_denials`. `--json-schema` contains quotes, so it needs the native `claude.exe` on Windows (see below). The prompt goes on stdin, never argv (Windows limits command-line length). When `claude` resolves to a `.cmd`/`.bat` wrapper (an npm install on Windows), cmd.exe re-parses the command line, so arguments containing `"&|<>^%!` or newlines are rejected with `HarnessError`; the native `claude.exe` has no such limit. A process that cannot start (missing binary or `cwd`) also raises `HarnessError`. An output line over 64 MiB is dropped and replaced in the transcript by a `{"type":"fact_dropped_line"}` marker. The process gets the worker's environment (`build_env`) plus `CLAUDE_CODE_DISABLE_AUTO_MEMORY=1` (no auto-memory carried between runs or projects; `request.env` can override it) plus `request.env`. Every `rate_limit_event` line is parsed with `parse_rate_limit_info` and merged into `usage_windows` (the newer window by name wins); `rate_limited` is set when the run failed (an error result, or none) and either an event had `status: "rejected"` or the text matches `fact.core.claude_usage.LIMIT_TEXT_RE` (which also matches an API 429); Claude Code may go on after a rejected event, so a successful result is never a limit. A logged-in Claude Code finds its credentials through `HOME`/`USERPROFILE`; an `ANTHROPIC_API_KEY` in the environment `fact dev` starts from wins over that login and bills the API instead of the subscription, so leave it unset there.

A session can send several `result` messages: Claude Code wakes a stopped session when a background task it started finishes, and each wake ends with its own `result`, whose `usage` and `num_turns` cover only that part while `total_cost_usd` and `modelUsage` cover the whole session. The outcome comes from the final `result`; `num_turns` sums `num_turns` over every `result`, and `agent_step` logs each part (`result i/n: <subtype>, <turns> turns, session cost $x`). The rest comes from the final `result` message:

- `stop_reason` is its `subtype`: `success`, `error_max_turns`, `error_during_execution`; `no_result` when the process ended without one (then `final_message` is the tail of stderr).
- `final_message` is `result`, or the joined `errors` when there is no `result`.
- `is_error` is the message's `is_error`, or true for a non-zero exit code.
- Tokens come from its `modelUsage`, summed over its models (`inputTokens`, `cacheReadInputTokens`, `cacheCreationInputTokens`, `outputTokens`), or from its `usage` when `modelUsage` is missing. `usage.tokens_in` is `input_tokens + cache_creation_input_tokens + cache_read_input_tokens`, of which `usage.cache_write_tokens` is `cache_creation_input_tokens` and `usage.cache_read_tokens` is `cache_read_input_tokens`; `usage.tokens_out` is `output_tokens`; `usage.cost_usd` is `total_cost_usd`, or None when the message has none (never 0). `usage.turns` is `num_turns`.
- `usage.peak_context_tokens` is the largest `input_tokens + cache_read_input_tokens + cache_creation_input_tokens` of any main-session `assistant` message (one without a `parent_tool_use_id`; a subagent's turns do not count), also for a session cut short.
- Without a `result` message (`no_result`), and in `agent_step` when the session is cancelled or crashes (`StepContext.reported_usage`), `usage` sums the `usage` of the `assistant` messages received, the last per `message.id` (`fact.worker.harnesses.claude_code_usage.StreamUsage`), with `partial=True`, `cost_usd=None` and `turns` the number of distinct main-session `message.id`s: Claude Code reports no cost per message, and fact never estimates one. These are the counts the messages carried; a message's `output_tokens` may be lower than its final count. A session that sent no `assistant` message never ran: its usage is empty and not marked partial. The step is stored with `usage_partial` and a NULL cost. Once `harness.run` returns, `reported_usage` is the result's full usage, so a step cancelled or failing after that (during the transcript upload, say) still records it with its cost.

Tests replay recorded streams from `tests/fixtures/claude_stream_*.jsonl` through `tests/fixtures/fake_claude.py`; no network. To re-record, run Claude Code once on a trivial prompt and strip local paths and the user's tool, plugin and MCP lists from the `init` message.

### Manual check

Runs real Claude Code (needs `claude` on PATH and logged in) on a prompt in a temporary folder and prints session id, cost, tokens and stop reason:

```
uv run python -m fact.worker.harnesses "reply with OK" --model haiku
```

## Agent step

`agent_step` (`fact.worker.activities.agent`, `sandbox` queue) runs a coding agent as a reported step, named after its prompt (`name` = `prompt_name`, such as `implement` or `fix_checks`). `AgentStepInput`: `run_id`, `stage_id`, `attempt`, `handle`, `task`, `prompt_name`, `context`, `complexity` (default `standard`), `override` (`RouteOverride`), `home_repo` (full name in `handle.repos`; default the first repository), `handoff_ref` (artifact key of a stopped run's handoff note, from `RunInput.handoff_ref`). With `handoff_ref`, the note is read through the API (`StepReporter.download_text`) and rendered as `$handoff`; a missing or unreadable note leaves `$handoff` empty, and the step log says which. The workflow runs it with `WAIT_CANCELLATION_COMPLETED`, so on a stop the cancellation reaches the activity at its next heartbeat and the workflow waits until the session has stopped before tearing the workspace down.

1. Picks harness and model with `routing.choose` from the step input's `routing` (the run's project config) and renders `.fact/prompts/<prompt_name>.md` from the home repository's worktree, so the prompt comes from the run's branch. The output schema is `prompts.BASE_OUTPUT_SCHEMA` (`status: done|blocked`, `summary`, optional `blocker`) plus the properties of `.fact/prompts/<prompt_name>.schema.json` when present.
2. Runs the harness with `cwd` = workspace root, and the step input's `max_turns` and `permission_mode` (the SDK's defaults under the project's `step_defaults.agent`); reports the turn count (distinct assistant message ids) and the session id to the worker's heartbeats on every message.
3. Uploads `transcript.jsonl` as the step's `transcript_ref` (`StepContext.attach_transcript`), also on error or cancel. Each denied tool call is a `permission denied:` line in the step log.
4. Returns the step's result with `session_id`. Heartbeats carry `(progress, session_id)`; if the worker shuts down during the session, the step fails with a non-retryable `ApplicationError` of type `AGENT_INTERRUPTED` whose `details[0]` is the session id, so the workflow can resume it.
5. With `resume_session_id` set, the harness resumes that session with `prompts.render_resume(context)` instead of the stage's prompt; the output schema is still the stage prompt's.
6. Sends the usage windows the run saw, if any, to `PUT /api/v1/usage/claude` (`StepReporter.report_usage`, best effort; one account, `claude`, until runner pools exist).
7. A `rate_limited` result ends the step `rate_limited`, with `outputs` `resume_at` (ISO: `ClaudeUsage.resume_at(1.0)`, when every refused or full window has reset plus 90 s; now plus 30 min when no window is known or the reset is already past) and `session_id`. `FactWorkflow.agent` sleeps on a durable timer until `resume_at` and resumes the same session (see `fact.sdk.agents`).
8. Otherwise `judge` turns the result into outcome, summary and outputs: the structured answer is the step's outputs (at most 64 KiB, else `failed_error`), plus `permission_denials` when there were any.

Outcomes: `passed` for `status: done`; `needs_human` for `status: blocked` (the summary is the `blocker`, followed by the denied tools); `failed_error` for an error result, a `HarnessError` or no structured answer; `stopped_by_monitor` when the stop reason is `error_max_turns`; `rate_limited` when the usage limit refused the session. The exit code alone never makes a step pass. An unknown harness, a missing home repository or prompt, a bad placeholder or an invalid `<prompt>.schema.json` raises a non-retryable `ApplicationError` (the step row is still finished as `failed_error`).

**Usage limits.** A `rate_limited` step is not a failure. `FactWorkflow.agent` (`fact.sdk.agents`) marks the run `waiting` (`record_run_waiting`), sets the `status` query's `waiting` to `usage limit until <YYYY-MM-DD HH:MM> UTC` (shown by `fact status` as `Waiting:`), sleeps with `workflow.sleep` until `resume_at` (no upper bound: a full weekly window means days), marks the run `running` again and resumes the same session as the next attempt, with the context `fact.sdk.sessions.LIMIT_PAUSED`; a step that never started a session is started over with its first context. These pauses do not count against `MAX_RESUMES`; after `MAX_LIMIT_PAUSES` (20) per `agent` call, one more limit ends the step `needs_human`. A stop during the sleep cancels the timer and ends the run `stopped`.

No `env` is passed to the harness yet, so only a Claude Code login found through `HOME`/`USERPROFILE` works; `ANTHROPIC_API_KEY` is not forwarded. `step_defaults.*.timeout_minutes` sets the agent and shell activities' maximum duration (resolved by `fact.sdk.step_defaults`).

## Open the PR

`open_change_set` (`fact.worker.activities.change_set`, `control` queue, stage `open_pr`, step kind `github`) pushes the run's branch and opens or updates its PR. It holds the GitHub App, so it runs only in the control zone. `OpenChangeSetInput`: `run_id`, `task`, `handle`, `branch` (the branch the workspace actually checked out, from `WorkspaceHandle.branches`), `title`, `summary`, `check_results` (`CheckResult`: `name`, `outcome`, `summary`), `criteria` (`CriterionResult`: `text`, `met`, `evidence`, from the review), `run_url`, `attempt` (of stage `open_pr`, default 1; `FactWorkflow.push_change_set` pushes again after a CI fix as the next attempt). It returns `list[PRRef]` (repository, number, URL, head SHA).

1. v0 supports exactly one repository in the handle. The worktree must have `branch` checked out; a detached HEAD or another branch is refused.
2. Reads the repository (`pull_requests.repo_info`: default branch, web URL) with an installation token, then `git_push.push_branch` pushes `refs/heads/<branch>` to an explicit URL (not the worktree's `origin`), with the user's git config and hooks. The default branch and names starting with `-` are refused. The token reaches git only through `GIT_CONFIG_COUNT`/`KEY_n`/`VALUE_n` as an `http.<url>.extraHeader` (Basic `x-access-token`); the same environment empties `credential.helper`, `core.askPass` and `GIT_ASKPASS`, so a rejected token fails the push instead of prompting or falling back to the user's credentials. Output lines are redacted and go to the step log.
3. Renders the body (`pr_body.render_pr_body`, `string.Template` over `templates/pr_body.md`): summary, the task (a file task's id linked to its file on the default branch; an issue as `owner/repo#n`, followed by `Closes owner/repo#n` for a single-PR change set or `Part of owner/repo#n` for several, `pr_count`), an `## Assumptions` section after the summary (a line when a session found the spec ambiguous, then the agent sessions' `assumptions` as a list; absent when there are neither), acceptance criteria as the review's table (criterion, met or not, evidence), or as a checklist when there was no review, check results, run link. Bodies over 65,000 characters are truncated.
4. Reuses the open PR from `<owner>:<branch>` into the default branch (only its body is replaced) or creates one.

A missing GitHub App, a refusal, and GitHub 401, 404 or 422 are non-retryable `ApplicationError`s; other errors retry. `python -m fact.worker` takes the process's one `GitHubApp` from `fact.core.github.shared_app` when configured and logs `github_app_unavailable` otherwise (then this activity fails and commits use the settings identity).

## Cost comment

`post_cost_comment(PostCostCommentInput)` (`fact.worker.activities.cost_comment.CostCommentActivities(github, api_base_url, http_client)`, `control` queue, not reported as a step; M1-16) reads `GET /api/v1/runs/{run_id}` with its steps and puts the run's time and cost on each PR in `prs`. `cost_comment.render_cost_comment` writes a markdown table of every step (stage with the step's name as `stage:name`, such as `checks:lint`, totals unlabelled; attempt, harness / model, wall-time duration or `running`, human wait, turns, peak context, uncached input, cache read, cache write and output tokens, cost) with a totals row (every column summed but peak context, which shows the largest step's), then a table per harness and model with the same usage columns; the footnote defines each column. A NULL cost reads `unknown` (a cut-short session is marked `(cut short)`); totals add only the known costs and say how many agent steps have none. The comment starts with `<!-- fact:cost -->`: `upsert_comment` pages through the PR's issue comments and updates the one carrying the marker, or creates it. A missing GitHub App, an unknown run (API 4xx) and GitHub 401, 404 or 422 are non-retryable. `FactWorkflow.post_cost_comment(prs)` treats any failure as a warning: the PR is already open. `FactWorkflow.execute` calls it once, as the run's last step after its outcome is recorded, on every ending (merged, closed, failed, needs_human, stopped) that opened a PR, so the comment covers every step; a cancelled run gets it too, since a stop is a cancellation request the workflow handles. Only a terminated workflow skips it.

## Wait for CI

`wait_for_ci(WaitForCIInput) -> StepResult` (`fact.worker.activities.ci.CIActivities(github, reporter, poll_interval_s=30)`, `control` queue, stage `wait_for_ci` by default, step kind `github`; M1-19). `WaitForCIInput`: `run_id`, `stage_id`, `attempt`, `pr` (`PRRef`), `timeout_s` (3600), `no_checks_grace_s` (300). GitHub reads are in `fact.worker.ci_checks`.

1. Polls the PR head SHA every 30 s: check runs (latest per name, GitHub's default filter, up to 10 pages of 100) and commit statuses (the combined status), each normalized to a `CICheck`. A check run of the `github-actions` app carries its job id. `success`, `neutral` and `skipped` pass; any other conclusion fails.
2. Heartbeats with its wall-clock start, so a retried attempt keeps the same deadline (the workflow sets the activity's start-to-close to 65 min and `INFRA_RETRY`).
3. Finishes when every check is complete on two polls in a row, so suites that start late (`needs:`, other workflows) get time. While no check or status has appeared, each poll also reads the PR's `mergeable_state` once (`pull_requests.merge_state`, which counts an answer about another head SHA, or `mergeable: null`, as not known yet): `dirty` (it conflicts with its base, and GitHub starts no `pull_request` workflow on it) ends the step at once, `failed_checks` with `outputs.conflict = true`, which `until_ci_green` hands to `sync_with_base`. No check at all after `no_checks_grace_s` without a known conflict is `passed` ("no CI checks"). A transient error reading the PR only skips a poll. A transient GitHub or network error only skips a poll; 401, 404 and 422 are non-retryable, as is a missing GitHub App.
4. Outcome `passed`, or `failed_checks` with `outputs` `head_sha`, `checks`, `pending` and `failures`: per failed check `name`, `conclusion`, `url`, `log_tail` (last 4 KB) and, for a GitHub Actions job (the first 10), `log_ref`. The job log is downloaded (GitHub redirects to a signed URL), stripped of the BOM and per-line timestamps, and stored whole as the step artifact `runs/<run>/<stage>/<attempt>/job-<id>.log`; an unreachable or expired log falls back to the check's output text. Other checks use their output text or the status description. The summary (2 KB cap) lists the failed names plus as much of the tails as fits.
5. At `timeout_s`, failures already known are still reported as above; with none, `failed_checks` with `outputs.timed_out = true` and `pending` (check names).

`FactWorkflow.until_ci_green` (in `fact.sdk.pull_requests`) feeds `outputs.failures` to the fix session through `fact.sdk.failures.ci_failure_context`; it does not start a fix after a timeout.

## Merge the base branch

`sync_base(SyncBaseInput) -> StepResult` (`WorkspaceActivities.sync_base`, the workspace's queue (`sandbox`), stage `sync_base` by default, step kind `shell`). `SyncBaseInput`: `run_id`, `handle`, `repos` (`RepoCheckout`s), `stage_id`, `attempt`, `verify_only`. For each repository it calls `Runner.fetch(handle, full_name)` (`LocalRunner`: `git fetch --prune origin` in the workspace's clone), then `fact.worker.base_merge.merge_base`, which runs git in the worktree through `Runner.exec`:

1. A merge still in progress (`MERGE_HEAD`): its unmerged paths, or, with none left, `git commit --no-edit` to conclude it (an agent may leave it resolved and staged).
2. `origin/<default_branch>` already in `HEAD`: up to date.
3. With `verify_only` (after a resolve session), stop there: `up_to_date`, even if the base moved on. Else `git merge --no-edit origin/<default_branch>`: a merge commit (the PR is squashed in the end, so nothing is rebased or force-pushed). On conflicts the merge stays in progress, markers and all, for a `resolve_conflicts` session.

It runs only when GitHub says the PR must take the base (it conflicts, or a merge was refused as out of date), never because the base moved on; after a resolution it only checks the merge is concluded and never merges a base that moved on meanwhile. Outcome `passed`, or `failed_checks` on a conflict; `outputs.merged` lists the repositories that got a merge commit, `outputs.conflicts` the unmerged paths per repository. A failed fetch raises `RunnerError`, which Temporal retries; the merge failing another way (a dirty worktree, a missing branch) is a non-retryable `ApplicationError`. The activity heartbeats every 30 s, so an attempt is abandoned only when its worker is gone or stuck, and Temporal then cancels it at its next heartbeat; the workflow waits for that cancellation (`WAIT_CANCELLED`) before a stop tears the worktree down. There is no in-process lock: a retry on another worker or after a restart would not see it. Nothing is pushed: the workflow pushes with `push_change_set`.

## Wait for review

`wait_for_review(WaitForReviewInput) -> list[ReviewEvent]` (`fact.worker.activities.review_wait.ReviewWaitActivities(github, poll_interval_s=60)`, `control` queue). `WaitForReviewInput`: `run_id`, `prs` (the PRs still open), `handled_reviews` (review ids the run already acted on), `reviews_since` (the run's start: older reviews, on a PR an earlier run of the task opened, were that run's to answer, so they are ignored). Every 60 s (the worker's `HeartbeatInterceptor` heartbeats meanwhile) it reads `GET /repos/{repo}/pulls/{number}` and, for an open PR, its reviews (`/reviews`, every page), and returns as soon as a round finds an event, at most one per PR, in order (`fact.worker.reviews.review_event`): `merged`, `closed`, then the first `CHANGES_REQUESTED` review not handled, then an `APPROVED` review whose `commit_id` is the PR's current head, not handled and newer than every `CHANGES_REQUESTED` review. Only maintainers' reviews count: a person with `admin` or `write` (GitHub reports `maintain` as `write`) from `GET /repos/{repo}/collaborators/{login}/permission` (`fact.worker.reviews.Maintainers`, each login looked up once per activity call; a 404 is not a maintainer). Anyone else's review is skipped as if it were not there: never returned, never handled, and it hides no maintainer's change request. Each review (but a `COMMENTED` one with no body, the envelope of its inline comments) and comment by a person who is not a maintainer, submitted since `reviews_since`, gets one fixed reply from `fact[bot]` (`fact.worker.outsiders`, no agent): a PR comment linking a review or conversation comment, a thread reply to an inline comment, saying only people with write access can steer fact. Each carries `<!-- fact:ignored <id> -->` and is skipped when that marker is already on the PR, so polls, retries and restarts post it once; each is logged once at info (`review_ignored` or `comment_ignored`: login, id, reason `not_maintainer`, never the body); a failed reply is logged and the wait goes on. Each `ReviewEvent` carries the PR at GitHub's current head, the review id and the reviewer's login. A transient GitHub or network error reading the PR only skips a poll; a permission lookup that fails other than with a 404 fails the attempt (retried; the author is never counted by default); 401, 404 and 422, and a missing GitHub App, are non-retryable. It reports no step: `FactWorkflow.wait_for_review` (in `fact.sdk.review_wait`) records each wait as a gate-like step (stage `wait_for_review`, kind `gate`) and gives it what is left of the run's 30 days (`REVIEW_TIMEOUT`) with `LONG_WAIT_RETRY`, so worker restarts do not use up its attempts.

## Conversation activities

`fact.worker.activities.conversation.ConversationActivities(github)`, `control` queue, all as the GitHub App (`fact[bot]`); a transient error is retried, 401 and 404 and a missing App are not.

- `collect_comments(CollectCommentsInput) -> list[Comment]`: maintainers' comments (bots and people without write access left out, by the same permission lookup; a failed lookup fails the attempt) on a PR (`pull_request: true`: review bodies, inline review comments, conversation comments) or an issue (conversation comments only), oldest first, made at or after `since`, plus every comment of review `review_id` whatever its time. Each `Comment` has its id, kind (`review`, `review_comment`, `comment`), author, body, time, URL, and for an inline one its path, line, review and thread.
- `post_replies(PostRepliesInput) -> int`: posts each `{comment_id, body}` reply: in its thread for an inline review comment (`POST /pulls/{n}/comments/{thread}/replies`, on the thread's first comment), else a PR or issue comment quoting what it answers. Each carries a hidden `<!-- fact:reply <key>:<comment id> -->` marker and is skipped when one is already there, so a retry never posts twice; a reply to a comment not in `comments` is dropped. Threads are never resolved.
- `request_review(RequestReviewInput)`: `POST /pulls/{n}/requested_reviewers`; a 422 (such as a reviewer without access) is logged, not raised.

## Control activities

`fact.worker.activities.control.ControlActivities(api_base_url, http_client, settings=None)` (settings default to `get_settings()`), `control` queue. None of them is reported as a step.

- `classify_signals(ClassifySignalsInput)` (`activities/classify.py`, `ClassifyActivities`): the deterministic half of classify, no LLM. Loads `.fact/project.yaml` from the project's local checkout (`project_path`, never the run's branch, so a change cannot loosen its own rules; no checkout or a bad file is non-retryable). For each repository, diffs `HEAD` against its merge base with `origin/<default_branch>` and returns a `ClassifySignal` per signal with the `ChangedPath`s that raised it: `schema_change`, `api_change`, `always_review` when a path matches `classify.schema_paths`, `api_paths` or `always_review_paths` (`PurePosixPath.full_match`, `**` spans folders); `api_breaking` when a JSON file under `api_paths` lost or changed any key, array element or value (additions alone are only `api_change`); `task_closed` (no paths) when `TaskSource.is_closed` says the task was closed meanwhile (skipped with a `task_source_unavailable` warning while the GitHub App is not configured). Not reported as a step; `FactWorkflow.classify` calls it once CI is green.
- `label_change_set(LabelChangeSetInput)` (`activities/change_set.py`, `ChangeSetActivities`, control queue, stage `label_prs`, step kind `github`): for a classified change set, re-renders each PR's description with its `## Review` section (`pr_body.py`: the route and its reasons, the signals with their paths, risk and door with their reasons, the security findings) and puts `fact:auto-merge` or `fact:needs-review` on the PR, removing the other, so it carries exactly one. The step's `outputs.classification` holds the `Classification`. Later `open_change_set` pushes keep the section (the classification rides in `OpenChangeSetInput.classification`). 401/404/422 or a missing App fail non-retryably.
- `report_status(ReportStatusInput)` (`activities/task_status.py`): loads the project's `.fact/project.yaml` from its local checkout (`project_path`), opens its source with `source_for` and applies the event with `fact.core.tasks.events.report`. No checkout, or a `github` source whose App is not configured (`task_source_unavailable` warning): logged and skipped; a bad `project.yaml` is non-retryable. A GitHub 4xx other than 429 (no access, no such issue, refused) is a non-retryable `ApplicationError`, since retrying only delays the run; 429, 5xx and network errors retry under `INFRA_RETRY`. Since M2-11, `FactWorkflow.report_task` (in `fact.sdk.task_status`) sends it, best effort: `run_started`, `gate_opened`, `gate_answered`, `prs_opened`, and the ends `merged`, `closed`, `stopped`, `needs_human` and `pr_opened` (see `docs/ARCHITECTURE.md`); all but `merged` hold the task with `fact:needs-human`.
- `mark_task_done(MarkTaskDoneInput) -> bool`: in the home repository's worktree (`home_repo`, default the first), deletes the task's file (`Task.path`, read from the default branch when the run started) and commits only that deletion as `chore(<id>): mark done`. Git runs with the user's config and the repository's hooks, with literal pathspecs and signing off; the environment is the minimal one `run_git` builds. A commit refused by a hook is non-retryable. Idempotent: a file already deleted on the branch (by an earlier attempt or by the agent) returns False; deleted but uncommitted is committed. An issue task (a `gh:` key with no path) returns False at once: the issue is closed by the run's `merged` event (M2-11), not by a commit. The task source comes from `source_for`; returns False when it cannot be opened (a `github` source with no App configured). A task without a path, a missing home repository or a bad `project.yaml` is non-retryable.
- `record_run_waiting(RunWaitingInput)`: `PATCH /api/v1/runs/{id}` with `waiting` (`waiting: true`) or `running`; `FactWorkflow.agent` calls it, best effort, around the sleep for a usage limit.
- `record_run_started(RunStartedInput)` and `record_run_finished(RunFinishedInput)`: `PATCH /api/v1/runs/{id}` with `running`/`started_at` (plus `worker_version` and `home_sha` when the run is versioned), or `finished`/`outcome`/`ended_at`. A 4xx is non-retryable; other errors are left to the retry policy. `FactWorkflow` treats a failure as a warning, not a run failure.

## Gate activities

`fact.worker.activities.gates.GateActivities(api_base_url, http_client)`, `control` queue (M2-01). `FactWorkflow.gate` (in `fact.sdk.human`) calls them around its wait, best effort: a failure only logs a warning, and the gate still holds the run.

- `record_gate_opened(GateOpenedInput) -> str`: creates the gate's step (`POST /api/v1/runs/{id}/steps`, kind `gate`, the gate's stage and attempt, `queued_at` and `started_at` = `opened_at`, the workflow time), PATCHes it to `waiting` with `outputs` `gate_id`, `kind`, `details`, PATCHes the run to `waiting`, and returns the step id. A retry is idempotent: the API returns the step the first attempt created.
- `record_gate_answered(GateAnsweredInput)`: PATCHes the step `finished` with `outcome` (`passed` for approve, `needs_human` for reject), `started_at`/`ended_at` (opened and answered, in workflow time), `wait_seconds` (the whole wall time, so the step's machine time is 0 and the run's `human_wait_seconds` gets it) and `outputs` plus `decision` and `note`; then the run back to `running`. With `step_id` None (the open was not recorded) it creates the step first.

A 4xx is a non-retryable `ApplicationError`; a 5xx or network error is left to `INFRA_RETRY`. Answering a gate (the `answer_gate` update) is done by a client: `POST /api/v1/runs/{id}/gates/{gate_id}` or `fact gate` (M2-02).

## Notify activity

`fact.worker.activities.notify.NotifyActivities(api_base_url, http_client)`, `control` queue (M2-03). Not reported as a step.

- `notify(NotifyInput) -> int`: `POST /api/v1/notifications` with the run id, `kind`, `title`, `body`, `link` and `dedupe_key`, and returns the notification's id. The API keeps one notification per `dedupe_key` (200 with the existing one on a repeat), so a retry never duplicates it. A 4xx is a non-retryable `ApplicationError`; a 5xx or network error is left to the retry policy.

`FactWorkflow.notify` (in `fact.sdk.human`) calls it best effort, with dedupe key `<run_id>:<key or kind>`: a failure only logs a warning. `FactWorkflow.gate` notifies `gate_waiting` once per gate; `Standard` calls `notify_prs_ready` once CI is green, before waiting for review, and `notify_run_end` when the run ends; `FactWorkflow.report_end` sends `task_held` (key `held`) for an end that holds the task (`stopped`, `needs_human`, `pr_opened`, `closed`). `tests/test_standard_notify.py` covers `Standard`'s notifications against the fake activities.

## Handoff note

`fact.worker.activities.handoff.HandoffActivities(api_base_url, http_client)`, `control` queue (M2-06). Not reported as a step.

- `write_handoff(HandoffInput) -> str`: renders the note with `fact.worker.handoff.render_handoff` (heading `## Handoff from a stopped run`, the reason, the last stage and attempt reached, the open PR links, then each agent step's stage, attempt, outcome and summary) and stores it with `PUT /api/v1/artifacts/<key>` at `fact.core.artifacts.handoff_key(run_id)` (`runs/<run_id>/handoff.md`); returns the key. The key is the run's, so a retry overwrites the same note. A 4xx is non-retryable; a 5xx or network error is left to the retry policy.

`FactWorkflow.stop` (in `fact.sdk.stop`) calls it best effort when a person stops the run, before tearing the workspace down and recording `stopped`. `POST /api/v1/runs/start` finds the newest note for the task (`fact.api.run_start.latest_handoff`) and passes its key as `RunInput.handoff_ref`; `agent_step` reads it back into `$handoff`.

## Scheduler

The scheduler is not in the worker: its tick runs in the API (`fact.api.scheduler.run_tick`, see `docs/ARCHITECTURE.md`), so Temporal runs only project workflows and an idle tick writes no workflow history. Before, a `fact-scheduler` Temporal Schedule started a `SchedulerTick` workflow every 30 s; `fact.worker.scheduler.delete_leftover_schedule(client)` runs at every worker start, after the project versions are made current, and deletes that Schedule if a dev Temporal database still has it (not found is fine). Tests: `tests/test_scheduler.py` (on `WorkflowEnvironment.start_local()`: the time-skipping server has no Schedules).

## Keep awake

`fact.worker.keep_awake` (M2-14, setting `worker.keep_awake`, default true). On Windows, `KeepAwake.set(active=True)` calls `SetThreadExecutionState(ES_CONTINUOUS | ES_SYSTEM_REQUIRED)` and `set(active=False)` releases it with `ES_CONTINUOUS`, calling Windows only when the wanted state changes; elsewhere it does nothing. `watch_active_runs` polls `GET /api/v1/scheduler/active` (runs queued, running or waiting) every 60 s and holds while the count is above zero; an unreachable API or a bad answer logs `keep_awake_poll_failed` and keeps the state; cancelling it (worker stop) releases. The hold lasts only while the calling thread lives, so it runs on the worker's event-loop thread from `python -m fact.worker`, never through `asyncio.to_thread` or an executor. Tests: `tests/test_keep_awake.py` (mocked `kernel32`).

## Prompts

`fact.worker.prompts.render_prompt` substitutes with `string.Template`: `$task_id`, `$task_title`, `$task_body`, `$acceptance_criteria` (one `- ` line per criterion), `$context`, `$workspace`, `$stage_id`, `$handoff` (a stopped run's handoff note, else empty). `$$` is a literal `$`; an unknown placeholder raises `PromptError`. Prompt names must match `[A-Za-z0-9][A-Za-z0-9_-]*`.

## Routing

`fact.worker.routing.choose(complexity, stage, routing, override=None) -> Route` reads the run's project `routing` (`.fact/project.yaml`, carried on `AgentStepInput.routing`). Each field, harness and model, comes separately from the first entry that sets it, in this order: `override`, `<complexity>.<stage>`, `<complexity>.*`, `*.<stage>`, else `routing.default` (`claude-code` / `sonnet`). Rule keys are validated as `<complexity|*>.<stage|*>`.
