# Backlog

Ideas and problems that are not yet tasks. Planning turns them into task files (or, after M2, issues).

## Human actions

Some steps can only be done by a person: downloading the GitHub App private key, installing the App on a repository, installing the Temporal CLI, logging Claude Code in, approving a permission. Tasks list them in `human_actions`, but fact has no way yet to ask for them and track them.

Needs a design for:
- how a workflow or task declares a human action, and blocks on it;
- how the person is asked (inbox, notification);
- how they confirm it is done, and how fact checks it where it can (for example, the key file exists and a token can be minted);
- reminders when a request waits too long.

It probably builds on the gate and notification work in M2 (M2-01 to M2-03).

## Workspaces

- Workspaces of runs that did not open their PR (failed, needs_human, cancelled) stay in `workspaces_dir` forever. Add `fact workspaces prune`: list them with their run status and remove the ones a person picks (a removed folder frees its branch, and the next run resets it to the remote). Until then, a left-behind workspace holding a task branch sends every new run on that task to a suffixed branch and a new PR.

## GitHub Issues source

- `GitHubIssuesSource.list_ready` reads each ready issue's blocked-by links and unknown dependencies one request at a time, every scheduler tick. Fine for a handful of issues; with dozens, fetch concurrently (bounded) or move to webhooks with hosting.
- `type:incident` maps to task type `bug` (M2-09): `TaskType` has no `incident`, so an incident runs the bug workflow. Add the type if incidents need their own workflow.
- M2-09 acceptance criterion "`fact run gh:Kahncode/fact#<n>` on a throwaway issue starts a run" was not checked by hand (unattended session): it needs a registered project with `task_source: {kind: github, repo: Kahncode/fact}` (fact itself is still `kind: files` until M2-12) and the App's Issues read permission. The path is covered by `api/tests/test_github_tasks.py` against a fake GitHub. M2-09 was run with `status: planned` (invoked explicitly).
- The PR description links file tasks to their file; an issue task shows only `#<n>: title`. Link the issue (and `Closes #n` where wanted); M2-11 did not, it comments the PR links on the issue instead.
- Duplicate comments (M2-11 follow-up): a retried `report_status` or a resumed run can post the same comment again (for example the PR links after a restart). Tag each comment with a hidden `<!-- fact:run:<id>:<event> -->` marker and skip the post when the issue already has it.
- Nothing calls `write_context` yet (M2-11 follow-up): decide what context the factory writes into the issue body, and whether the reader should strip the context section from `Task.body` and the acceptance criteria.
- `report_status` treats every GitHub 4xx but 429 as permanent (M2-11 follow-up), so a 403 secondary rate limit is not retried and the event is lost; detect it (`retry-after`, `x-ratelimit-remaining: 0`) and retry.

- `database_url` builds the SQLite URL by string interpolation; a `data_dir` containing `?` or `#` is misparsed. Use `URL.create` and add a test with such a path (found in M0-05 review).

- `GET /api/v1/runs` has no pagination (limit/offset); add before run lists grow (found in M1-03 review).
- `POST /runs/{id}/events` checks each `step_id` with its own query and has no batch size cap; use one `IN` query and a max length (M1-03 review).
- Run totals are recomputed read-then-write; concurrent step finishes could lose an update on Postgres. Lock the run row or use one `UPDATE ... SELECT sum` when moving off SQLite (M1-03 review).

- Artifact API (from M1-04 review): no upload size limit (return 413) and no auth on `PUT`/`GET /api/v1/artifacts/*`; add both before the API is exposed beyond localhost. Sweep stale files in `<artifacts>/.tmp/` at startup. `put_stream` is not on the `ArtifactStore` protocol; add it (or an equivalent) when the S3 backend arrives.

- Worker tests import `fact.api` but `fact-api` is not a declared dev dependency of `worker`; add a dev group to `worker/pyproject.toml` (found in M1-05 review).

Mirror lock is in-process only; use a file lock when several workers share `repos_dir`. On Windows, descendants of an already-exited leader survive `taskkill /T`; use a Job Object if it matters.

- M1-07 review: `StepResult.summary` is capped at 2 KB (`SUMMARY_MAX_BYTES`), so `shell_step` puts the last 2 KB in `summary` and the last 4 KB in `outputs["failure_output"]`; M1-12's fix prompt should read `outputs`. `prepare_workspace` does not heartbeat (workflows must not set a heartbeat timeout on it yet) and has no failure test. No cancellation test for `shell_step`. Move queue constants out of `ping.py`. `outputs["command"]` stores argv, so repo commands must not contain secrets.

- Claude credentials for sessions and usage (checked by hand 2026-11-26: the usage endpoint answers a `claude setup-token` token with 403 Forbidden; the token is valid, it lacks the scope). Split the two uses:
  - **Sessions:** agent sessions should run on the long-lived `setup-token` token (passed to the harness as `CLAUDE_CODE_OAUTH_TOKEN`), not the CLI login under `HOME`/`USERPROFILE`, so a session can run on a remote machine with no interactive login. Today no `env` reaches the harness (worker README), so this needs a credential setting and the harness to forward it.
  - **Several accounts:** a credential pool with fallback, for example a proxy like [dario](https://github.com/askalf/dario), so a session moves to another account's credentials when one hits its limit. Evaluate before designing the pool ourselves.
  - **Usage:** M2-14 reads usage with the local Claude Code login only. For a remote worker, the orchestrator checks usage itself with OAuth credentials that carry the profile scope, holding the refresh token and refreshing the access token on its own, instead of reading the token the Claude Code CLI stores and refreshes (`read_cli_token`). With a pool, it checks each account's windows.

- Drop and restart (M2-06): a drop is processed by the run's own pinned worker version, so a run whose version no worker runs (the usual reason to drop after a restart on new code) or one started before M2-06 never ends: its row stays unfinished and its workspace holds the task branch, so the restart gets `<branch>-2` and a new PR. A cancel now ends the run `dropped`, which settles the M1-12 note about cancelled runs never recorded as finished. Acceptance was checked with tests (mocked GitHub), not a live fact run. M2-06 was run with `status: planned` (invoked explicitly).

A usage-limit pause sends no notification. `rate_limited` needs the run to have failed: a rejected `rate_limit_event` followed by a successful result is not a limit (unattended decision; the task asked for rejected events alone). `AgentSteps.agent` was moved out of `workflow.py` (~80 lines) to keep it under 300 lines; done unattended without asking. Acceptance was checked with tests, not a live fact run. M2-13 was run with `status: planned` (invoked explicitly).
